# Proposal for explicit Lens representation and subject selection

Recorded: 2026-10-06

Updated: 2026-10-11

Develop a sound request model exercised by every existing capability. The proposed scope is explicit Lens identity, applicability and parameter meaning; subject designation and resolution; selection independent of inspection construction; request reporting from the actual request and outcome; and preservation of the distinction between Lens requirements and reusable investigation operations. This addresses the representation audit's F1–F4, subject to checking implementation dependencies during planning. Ease of adding Lenses is an acceptance criterion for this work.

This remains an exploratory proposal, not a formal draft plan, accepted implementation decision or authorization to implement. The [research foundation](../foundation/product-design.md), [application specification](../docs/app-specification.md), [core concepts](../docs/core-concepts.md), [architectural constraints](../docs/architectural-constraints.md) and accepted decisions govern it. The [representation audit](../records/audits/2026-10-06-user-model-concept-representations/REPORT.md) supplies historical findings; its proposals are not requirements. The [backlog](../docs/backlog.md#candidates) records candidates rather than implementation commitments. Recommendations below describe the proposed design; where they depart from current contracts, the affected provisions are identified under [decision treatment](#proposed-reversals-and-decision-treatment) for explicit acceptance before implementation.

## Lens answers and coordinated Views

There is no distinct composite-Lens architectural category to implement. A Presentation can coordinate independently qualified Projections without manufacturing an outer Lens or Projection merely to combine their display or interaction. Each input retains its own meaning and qualification. A summary View need not imply a summary Lens.

A Lens can still use several analyses, evidence sources, reusable operation outcomes or qualified Projections to produce its own answer. The [accepted distinction](../docs/decisions/coordinated-views-and-qualified-results.md#generalize-lens-results-and-view-composition) depends on requested meaning: a Lens produces a qualified answer with its own subject, question and selection; a Presentation coordinates existing answers. New synthesis requires analysis. This is not a one-Lens/one-operation restriction or a prohibition on genuinely consumed component answers.

Choosing independent summary and dependency answers for a coordinated View is Projection selection. Refining the information a particular summary Lens is to synthesize is a Lens parameter. Neither becomes a request to execute arbitrary operations. The operation choices needed to satisfy a Lens remain implementation responsibilities under Evaluation.

Existing associated-inspection and embedded module results keep their accepted contracts. The coordinated-Views decision does not mandate migrating them into independent top-level Projections. Their presence is not itself an architecture contradiction. F4 is different: dependency construction creates an inspection answer only to copy its selection, without consuming that answer as an attributed qualified contribution.

## Meaning carried by a request

A request should keep the following responsibilities identifiable. This table describes semantics, not mandatory stored stages or a universal record schema.

| Information | Meaning |
| --- | --- |
| Lens identity | The investigative question selected. “Question” means the conceptual information need, not a user-supplied prose prompt. |
| Lens parameters | Values refining that question; currently empty for the implemented lenses. |
| Subject designation | How the subject is named: configured project, repository, literal name/handle or precise reference in the current capability set. |
| Resolution and application outcome | What the designation resolved to, on which population/basis, and whether the requested Lens and parameters apply. |
| Program-input designation and applicable binding | The program information the request concerns, kept separate from subject designation and Lens parameters. |
| Captured basis | The actual captured support used by the resulting Projection; a Session identifier or configured path alone is not that basis. |
| Presentation and execution inputs | Display choices, declared expansions and execution constraints, each retaining its own meaning. |

For the current API, the opened project's input context can remain session-bound rather than being repeated in every call. Planning should explain how normalized requests use that context and how results retain their existing qualified support. It must not relabel the current unchanged-input session as a following or pinned binding, or add speculative multi-input fields and capture identifiers merely to resemble the full product model. The architecture explicitly leaves representation choices open.

Respect explicit choices when selecting unspecified request elements. The [initial-View contract](../docs/app-specification.md#initial-views-and-further-investigation) does not prescribe a universal summary-first default. Opening a subject authorizes its initial answer only when the action communicates that behavior; it does not authorize unrelated exploration.

[Navigation context](../docs/app-specification.md#workspaces-and-navigation) is distinct from subject designation and evidence provenance. A supplied reference does not establish an origin View. Keep established origin where available and disclose missing origin; the known CLI lineage gap remains separate. A request model must not require a Workspace root or formal task to identify a subject.

Defaults and aliases should normalize before semantic validation, with the actual resolved choices available for reporting. Do not reconstruct a past request's explanation from later defaults. A request and its produced result remain distinct: missing subjects, unsupported applications and unavailable analysis must be describable without pretending the requested information was produced. Repeating a request is also distinct from presenting an exact retained Projection.

### Planning has its own outcome

Represent planning as an activity in its own right. Its outcome must cleanly express when it was unable to settle on a plan. A settled plan identifies the resolved subject selection, Lens and normalized parameters, applicable input context, and the information and presentation requirements to be fulfilled. It does not guarantee that subsequent Evaluation will succeed or fully materialize the requested answer. The exact plan representation remains an implementation choice; an explicit planning outcome does not require a general planner, workflow language or durable planning store.

When planning cannot settle a valid application, its outcome should preserve the request, the resolution achieved, relevant candidate subjects and qualifications, and the reason or information still needed. Represent missing subjects, ambiguity where one subject is required, invalid parameters and incompatible precise targets without constructing a Projection for the unsuccessful application. This changes current retention contracts and requires explicit decision treatment. The interface can explain the outcome and, where appropriate, ask for clarification. No new interactive clarification flow is required for the current CLI merely to represent that possibility. Multiple resolved subjects remain valid when the selected Lens accepts that collection.

Keep this distinct from a valid application whose qualified answer is empty or partial, and from evaluation failure or unavailability after a plan has been settled. If resolving the request required prerequisite analysis, preserve that work and its qualified results and outcomes as part of the request, even if planning ultimately cannot settle the requested application. When resolution consumes previously established information, preserve attribution to that information and its qualifications as well. An unsuccessful planning outcome does not imply that no work occurred or erase independently produced results. Unexpected invariant failures remain defects rather than ordinary unable-to-plan outcomes.

This would change the existing contract that retains some missing, ambiguous or unsupported investigation selections as Projections. The later decision package would need explicit acceptance and precise supersession of those provisions, together with the resulting CLI and structured-output changes. Until then those selections remain required. Reporting must describe what was actually retained and presented; under the proposed no-Projection outcome it must not fabricate a program View or view-produced event.

Keep planning outcomes interaction-scoped. Return a self-contained outcome to the caller, keep it available through execution and publication, and capture the actual request, resolution, choices and reasons in the command's observations. After the interaction completes, the session does not retain an independently addressable plan. Observation snapshots preserve the account of the interaction without creating a resumable plan or plan store. Planning resources should be released at completion; any program results or supporting records produced during the interaction retain their own established lifetimes. This does not change the separately deferred captured-basis observation export work.

Not retaining an independently addressable plan is compatible with the adopted architecture, which requires no such artifact. Removing an existing retained selection is a different lifecycle decision. The current implementation retains qualified investigation selections, not a general planning store. Immutability does not require indefinite retention, but that distinction does not cancel the existing Session retention contract. Observation reporting alone is not a substitute for current in-session addressability. Before accepting the removal, specify which unsuccessful selections disappear, how their supporting information remains inspectable, and which valid-but-unavailable or failed-result selections remain retained.

Preserve the [current interpretation outcome contract](../docs/decisions/investigator-execution-and-evidence-access.md#evaluation-outcomes-and-later-requests): accepted results, execution-limit stops and investigation failures have retained reusable evaluations; configuration and communication/service failures do not. The latter can nevertheless have retained selection Projections containing an immutable unavailable outcome under qualified construction. Interruption/invalidation ends the current Session with diagnostics and usage reported, without a reusable interrupted evaluation. Qualified mechanical evidence follows its own retention rules; unfinished interpretation is not accepted merely because some evidence was acquired. The proposed planning-outcome change does not alter these evaluation, retry, atomic-acceptance or cleanup semantics.

## Explicit Lens definitions

Use one canonical Lens identity vocabulary in normalized domain requests and results, with explicit CLI spelling mappings. A small typed set of definitions should state purpose, applicability, parameter meaning and information requirements. Keep those semantics available to dispatch, validation and request reporting without requiring those consumers to import renderers or constructors.

Prefer the existing semantic dependency names `dependency-structure`, `dependency-children` and `dependency-parents`, with their shorter CLI aliases, but settle identifier spellings and command mappings in planning. Exhaustive typing and runtime boundary validation should expose missing cases; inventory must not be a fallback description for an unrecognized Lens.

Applicability depends on the Lens, subject and parameter values. It is separate from analysis availability, execution success and materialization. Requirements may vary by subject and parameter values without changing Lens identity. The implemented definitions should cover current capabilities without treating the present subject kinds as an exhaustive domain ontology.

A Lens may use different underlying work for different subject kinds while retaining a coherent investigative purpose. That does not authorize silently changing dependency children into group containment or investigram composition. The meaning of the Lens, not the convenience of a shared command word, determines the supported application.

### Inspection and reporting

Use one `inspect` Lens identity. Module, group, mixed and exact-investigram inspection express qualified detail for the designated subjects while preserving their different selection and retention rules. Exact investigram inspection targets the immutable original and performs no inference. Associated inspection retains its mechanical basis and frozen association selection.

Under this proposal, the implementation is free, and encouraged where it keeps responsibilities clear, to make this Lens a thin layer over separate internal Lens implementations for the supported subject kinds. One Lens identity does not require one constructor, one record shape or one large conditional implementation. Subject-specific requirements, parameter validation and construction can live with those implementations; mixed inspection can coordinate the applicable implementations while preserving its accepted qualified selection. Requests and results would identify the shared Lens, with implementation method and provenance attributable separately. The shared identity is a proposal whose consequential contract belongs in the eventual decision package.

`usage` is already reporting, not a program Lens, and must not acquire a retained program Projection. The proposed request model should express that distinction directly. Removing its current lens-shaped compatibility descriptor is a separate proposed output change: the accepted qualified-construction decision expressly retains that descriptor. Remove the descriptor under the proposed experimental-output policy, replacing that specific prescription in the later decision package before implementation.

## Subject designation and qualified resolution

Retain designation, resolved targets, Lens applicability and qualified population selection separately. The investigation family's `SelectionSelector` is a useful starting point for literals and resolved/unresolved references, but its `null` case does not distinguish project from repository. This does not require replacing every record family with one shape.

Coordinate subject lookup during request/View planning through a shared, interface-independent resolution capability. It is not owned by the Lens implementation. Planning supplies the designation and intended lookup context; the resolver returns candidates and qualified resolution information; application checking uses the Lens's declared applicability and cardinality. Planning is responsible for supplying valid resolved subjects to the Lens implementation. Whether a Lens is chosen before or after full or partial name resolution is a planning responsibility and does not constrain the Lens implementation.

This separates planning from Presentation arrangement. Planning may request prerequisite investigation through analysis, Evaluation and core construction to establish qualified information for lookup; arrangement still consumes supplied qualified results without selector lookup or analysis. The existing CLI request coordinator can implement this responsibility without a general planner or a new mandatory stored planning stage.

The adopted [request-resolution contract](../docs/app-specification.md#interpreting-and-resolving-requests) makes the boundary explicit: planning may request and consume qualified information, but does not itself derive the lookup population or other program claims. Resolution must retain attribution to the information and qualifications behind its selection, ambiguity or inability to resolve. Established candidates, incomplete coverage and unavailable analysis must not disappear into an undifferentiated “not found.”

Under the adopted [initiation definition](../docs/core-concepts.md#investigation-initiation), prerequisite investigation PostCode initiates to resolve an explicit request is request-scoped system-initiated work. A human parent does not change its initiator. Merely choosing an unspecified Lens or Presentation to answer the expressed need is request interpretation; the selected answer remains explicitly requested work. Preserve this distinction rather than labeling every internal operation as another investigation.

Under the [initiation constraints](../docs/architectural-constraints.md#investigation-initiation-and-request-attribution), request-scoped work has an explicit parent and remains within its purpose, constraints and resource choices. Work outside that purpose or continuing after satisfaction or cancellation is autonomous, even if it originally arose while serving the request. Autonomous work requires human-authorized resource policies; hosted-service enablement alone is insufficient. Work exceeding those policies or materially delaying an explicit request remains deferred unless authorized. Initiator, parent or trigger, captured basis, results and qualifications must be inspectable from affected outcomes and attributable in observations. Reuse preserves original provenance and does not establish freshness; recording current consumption must not rewrite the reused result's origin.

The [Evaluation definition](../docs/core-concepts.md#evaluation) includes requirements from system-initiated investigation as well as Lens requirements and Presentation expansions.

For this proposal, trace prerequisite work in mechanical resolution, summary construction and investigator evidence access through request coordination, Evaluation and observation publication. Identify where initiation, parent/trigger, resource constraints, reuse and consequential outcomes are already represented and where they are missing. The [accepted assessment gap](../docs/backlog.md#assess-investigation-initiation-and-parent-attribution) is not proof that every path is defective. Choose record changes only after that trace. No event per helper call, universal investigation record, autonomous behavior or scheduling system is implied. The separate captured-basis export and navigation-origin gaps remain disclosed; accurate request labels alone do not establish complete attribution.

Resolve a precise reference to its actual target and kind before interpreting failure to match a Lens's population. Prefer a narrow read operation on the existing session binding service for known bindings. The present `entityIds` operation can allocate references; it is not a read-only reverse lookup. Do not infer existence from a prefix or allocate every retained subject merely to classify a request. Preserve valid-request allocation schedules and collision behavior. The arrangement-side binding port must remain binding-only.

When a Lens is selected, use its declared applicability to narrow name lookup to suitable candidates. If broader or partial resolution preceded Lens selection, planning refines or validates that result before invoking the Lens implementation. The resolver remains usable before a Lens is selected. Current dependency requests therefore continue to search module names/handles. A precise `children @group-…` request is different: its target must not be filtered into apparent nonexistence or silently retargeted. Planning resolves the group and reports the unsupported application without passing it to the dependency Lens. Missing information about a lookup population remains distinct from an established empty selection.

Lens implementations should defensively check that supplied subjects and normalized parameters satisfy their contract. Invalid input at that internal boundary is an invariant failure, not the normal route for rejecting a human's request. User-facing missing, ambiguous, invalid-parameter and unsupported-application outcomes belong to request coordination using the declared contract. Analysis availability and materialization remain separate: a valid application can still yield partial or unavailable information. Share contract definitions or validation logic rather than maintain competing applicability rules in planning and implementation.

| Existing request capability | Behavior to preserve or correct |
| --- | --- |
| Module inventory | Configured-project subject and qualified module population. |
| Organization for project or repository | Distinct population selection and its qualifications. |
| Dependency structure | Project structure, opaque endpoints and coverage distinctions. |
| Module, group and mixed inspection | All exact matches and legitimate embedded detail; no arbitrary selection of one match. |
| Dependency children and parents | Current direct module selection, including opaque external subjects; bound non-module targets produce an explicit unsupported outcome. |
| Module summary | One module; missing/ambiguous selection does not invoke investigation. |
| Explain, decompose and examine | One exact investigram; program-subject references are unsupported, not unknown. |
| Exact investigram and associated inspection | Original-target semantics and fixed retained correction/association selections. |
| Usage | Subjectless reporting through the same request/reporting infrastructure, outside Lens semantics. |

A bound group refusal should preserve its actual target and requested Lens, produce an accurate unsupported-subject description and leave the reference usable by subsequent inspection. The proposed planning-outcome design would do this without invoking the Lens or creating a Projection for the invalid application. That representation is not a prerequisite for fixing the false unknown-reference report. Removing existing unsupported-selection records elsewhere requires the explicit contract change described above. A known compatible target absent from a supplied evaluation population must retain that scope limitation rather than become an unknown reference. Applicability, reference status and evaluation materialization must not be compressed into one overloaded status.

Give otherwise identical qualified answers the same Projection identity regardless of subject designation. A name lookup and a precise reference resolving to the same subject should share Projection identity when the Lens, normalized parameters, captured basis, selected information, supporting method/evidence, qualification and relevant outcomes are otherwise the same. The same applies to different names or handles resolving to that subject. Preserve meaningful collection order or roles where applicable; this is not permission to equate distinct subjects or captures merely because their displayed content matches.

Designation and lookup provenance belong to the request and its resolution outcome, which can reference the resulting Projection. Preserve literal/reference modes, supplied spellings, missing/ambiguous outcomes and population-completeness information there, rather than making one invocation's lookup history part of a shared answer. The unresolved and subsequently resolved outcomes remain distinct without requiring an unresolved request to establish a program answer. Qualification that actually affects the Lens's selected population or answer still belongs to the Projection and must not be discarded to force identity equality.

This requires more than changing a hash: request-specific fields must be separated from immutable Projection payloads so two requests sharing an ID do not submit conflicting retained records. Plan the exact record, descriptor, comparison and method-version changes across all four families, including associated inspection and investigation selections. Existing accepted identity/retention provisions that encode designation in Projections need explicit treatment in the later decision package. No global content-deduplication service or cross-session identity guarantee is implied.

## Selection independent of inspection construction

Extract the matching and qualified selection responsibility currently embedded in module inspection into the shared resolution capability used by request coordination. Dependency construction should consume the resolved selection and retain its own answer without a discarded inspection Projection. Where module inspection and summary lookup have equivalent matching semantics, share that responsibility while preserving their different cardinality rules. Keep subject-name resolution distinct from the Lens's selection of information that answers its question.

The selection operation should consume an explicitly established population and its relevant support. It should not obtain broader matches by scanning unrelated accumulated information, initiate rendering or manufacture an unused Lens answer as a lookup side effect. Planning may first request prerequisite investigation through Evaluation and core construction; the resolver consumes its qualified results. A deliberately requested population Projection whose information and qualifications are genuinely consumed for resolution is legitimate. The F4 defect is copying selection from an otherwise unused inspection answer, not the mere existence of a prerequisite Projection. Separation does not imply that every request can be resolved before any evaluation, or require a Projection for every matching operation.

Preserve organization inspection's embedded module Projection and associated inspection's retained mechanical basis where those answers are genuinely consumed. There is no requirement for a universal component pointer or for converting these accepted selections into a multi-Projection View.

## Lens requirements and investigation operations

Keep the [accepted operation separation](../docs/decisions/investigation-operations-and-lenses.md). Lens requirements describe the information needed for the answer. Investigation operations describe reusable work with their own subject, parameters and relevant context. Evaluation determines compatible reuse and missing work; construction consumes materialized information and outcomes.

The duplicated current mappings in session dispatch and investigation selection should have one authoritative source. Their present one-to-one shape is a property of this slice, not a permanent restriction on Lens definitions. A different Lens must not force a new investigation when its requirement can use a compatible retained outcome. Conversely, sharing an operation name cannot justify reuse across incompatible subjects, parameters or method/context.

A prompt-backed operation can remain a small declarative entry with standard evidence access, validation, retention and reporting. Prompt/method changes that alter the work need explicit provenance and reuse treatment. A Lens definition must not bypass Evaluation by invoking an investigator directly. The existing single-operation dialogue contract remains unchanged; this work does not introduce multi-operation dialogues or a declarative composition engine.

An ordinary interpretive Lens should have a convenient authoring declaration supplying its identity and description, applicable subjects and parameters, the prompt defining the interpretive work, and any departures from standard context/evidence or result handling. One declaration may define both the Lens and its default reusable operation, without requiring the author to duplicate metadata merely to preserve the architectural distinction. Internally, Lens requirements and operation identity remain separate: Evaluation still owns execution and reuse, and another Lens can request the same compatible operation. Standard execution, validation, retention, presentation and reporting should work without Lens-specific edits in those common paths. Specialized implementations remain possible when their semantics require them. The exact declaration syntax and registration mechanism are not yet chosen.

## Request reporting from the actual request and outcome

Carry normalized request meaning and the actual resolution/application outcome through execution and publication. Observations should not infer a request from a View-wide Lens tag or reconstruct it from bounded arranged content. Record the requested Lens, designation and true parameter values separately from the produced Projection and outcome. Refused and failed requests still have an intelligible request even when no answer exists.

Describe navigation through its designation mode: precise session reference, literal lookup or scoped population request. Identify investigrams as subjects without implying they are entities. Every implemented Lens, including follow-ups and unsupported children/parents requests, must produce accurate reporting without a catch-all inventory description. Usage has a reporting-request description of its own.

Preserve command outcomes, actual output, usage finalization, source-disclosure classification and delivery behavior. The current singular schema can be corrected without implementing a plural View schema; future coordination will need associations between each actual request and result, rather than a single Lens attributed to an entire View.

The [captured-basis observation gap](../docs/backlog.md#preserve-captured-basis-attribution-in-observations) remains separate and explicitly deferred. This work may correct an associated-inspection request descriptor, but that alone does not establish adequate exported support after the ephemeral store is gone. Do not claim full provenance conformance or add historical observation migration under F1.

## Experimental structured outputs

For now, during early development, treat structured outputs as experimental and subject to change without notice. There are no known production consumers inside or outside PostCode; temporary GUI wireframes are not a reason to preserve the formats. Change affected JSON and observation payloads directly to express the new model, without compatibility aliases, dual formats, deprecation, adapters or migration. Historical observations remain untouched, with no new historical-reader promise. Replace the specific accepted schema prescriptions identified below when adopting this policy. Internal Presentation compatibility and preservation of qualified meaning remain requirements.

This is a development-stage policy, not the intended permanent external contract. Structured outputs will eventually need deliberate versioning and published schemas, with compatibility obligations defined for their consumers. Establish that policy when preparing the formats for supported use; do not introduce its infrastructure or maintenance burden into this early development work.

## Ease of adding Lenses as an acceptance criterion

Walk through both additions against the proposed design during planning and demonstrate the resulting integration approach during implementation verification. Record the actual changes required and why each belongs to the new capability. A prose assertion that a table is extensible is insufficient; a bounded fixture or test definition can demonstrate the path without shipping a new public Lens.

| Addition to exercise | Expected integration |
| --- | --- |
| An ordinary interpretive Lens over a currently supported subject and existing investigram/evidence contracts | Declare Lens identity, applicability and parameter meaning; select an existing operation or add an objective/prompt with the necessary operation metadata; reuse the existing execution, acceptance, retention, arrangement and reporting paths. |
| A mechanical Lens selecting a useful subset of already established module or dependency information | Declare the question and requirements; implement its qualified selection/construction; reuse subject resolution, reference handling, existing content/presentation facilities where suitable and request reporting. No new provider or analyzer is needed for this example. |

Pass when additions are local and understandable: capability-specific declarations and construction belong with that capability; common parsing, applicability handling and observations do not need another Lens-name conditional. A small explicit registration or CLI exposure change can be reasonable. New semantics may require any kind of implementation code appropriate to their responsibilities, not only selection or arrangement code. For presentation, reuse a suitable Presentation, modify one compatibly without breaking its existing uses, or create a new Presentation. The test is whether each necessary change serves the new semantics while preserving existing contracts, rather than repeating dispatch policy throughout the system.

The interpretive walkthrough can use a hypothetical module “risks” Lens with existing evidence access and investigram output. Use it to test the proposed single-declaration authoring convenience against actual integration needs, while keeping Lens identity separate from operation identity. A table or registry is not itself evidence of extensibility, and its syntax is not adopted. Reusing an operation should preserve its original provenance, and adding a prompt should not require copying the entire investigation path. The mechanical walkthrough can use a Lens selecting a module's established exports, declaring the existing export-information requirement without constructing an inspection answer to extract it. These are integration examples, not approval to ship either Lens or a claim about interpretation quality. The mechanical example must retain qualification, omissions and population meaning. Both need correct reporting and unsupported/missing-subject behavior without special reporting patches.

Both walkthroughs must preserve [captured-source disclosure](../docs/app-specification.md#source-escape-hatch) and the [generated-output evidence boundary](../docs/app-specification.md#generated-output-evidence-boundary). A reused Projection remains an attributed PostCode result, not independent corroboration of its own claims.

Aim for prompt plus minimal metadata in the ordinary interpretive case. Do not turn that aim into a promise that every new Lens needs only a prompt. Neither walkthrough justifies a plugin system, dynamic registration, a workflow language or a general planner.

### Matching Lens results to Presentations

Include an explicit, bounded contract mechanism in this work so planning can determine which available Presentations are appropriate for a Lens's result, even with only a few current result types. Every existing program View path must exercise it. Declared compatibility should replace implicit dispatch assumptions rather than become unused metadata beside them. Exact schema and API mechanics remain to be planned; this does not expand into general GUI Presentation design.

A Lens implementation declares the kind of qualified information its Projection exposes for the selected subject and parameters. A Presentation declares the input contracts it supports, any additional preconditions, supported presentation options and standard expansions it needs. Several lenses can supply the same contract, and several Presentations can consume it. An ordinary new interpretive Lens using the existing investigram contract should therefore be eligible for existing interpretation Presentations without a new Lens-name branch in each one. Different internal implementations of one Lens may expose different result contracts; the shared Lens identity alone is not enough to select a Presentation.

The contract must carry meaning as well as data shape: populations, relationship direction, identity/correspondence where relevant, qualification, materialization and permitted absent detail. A generic nodes-and-edges shape alone does not establish that a dependency-specific Presentation can honestly display containment or inferred relationships. Typed content interfaces and small explicit compatibility declarations or checks may suffice for current families; no structural-schema inference engine or universal Projection format is implied.

Planning distinguishes compatibility from preference. It determines which Presentations can consume the prospective result and requested options, then honors an explicit choice or selects among compatible choices using interface context and defaults. The choice and its criteria must remain inspectable. Where materialized content matters, planning can refine the choice after Evaluation or use a declared fallback; it must expose consequential changes rather than silently change the question or omit required qualification. No suitable Presentation is a View-planning problem, not evidence that the Lens is inapplicable to the subject.

Compatibility has a pre-execution and an actual-result aspect. Declared result contracts let planning choose a candidate and include its standard expansion requirements before Evaluation. Actual content and evaluation outcomes then determine what was materialized. A supported contract must account for empty, partial and unavailable cases: supplying less information is not permission to render a misleading complete answer. Any further evaluation needed for a revised choice returns through request coordination; arrangement cannot acquire it. Exact retained-Projection presentation would be limited to the content that result actually supplies, with richer information requiring another request under the separately scoped continuity rules.

The minimum mechanism should provide:

- Explicit identification of the qualified result contracts currently implemented, backed by their typed content and semantic guarantees. Do not force different meanings into one generic record shape or give every Lens a unique output type merely because its identity differs.
- A declaration of the prospective result contract from the chosen Lens implementation for the resolved subject and normalized parameters.
- Presentation declarations identifying accepted contracts, supported options, relevant preconditions and standard expansion requirements. Those requirements remain distinct from the Lens's own requirements.
- Actual planner use of those declarations to choose a compatible Presentation or explain why a requested View cannot be planned. Keep compatibility separate from default/preference policy and retain the choices actually made.
- Validation at the construction/arrangement boundary that the supplied result conforms to the selected contract. A programmer passing incompatible content is an invariant failure; expected partial or unavailable content remains an ordinary qualified result under its declared contract.

Use ordinary types and a small static catalog or explicit functions as sufficient for the current families; choose exact API mechanics during planning. Keep the concrete contract association available at runtime where the planner needs it, rather than relying only on compile-time types. Rich structural matching, automatic data conversion, contract inheritance, dynamic discovery and a general constraint solver are not necessary. An explicit adapter is possible when needed, but must preserve supplied meaning and qualification and cannot smuggle analysis into Presentation.

The full adopted model permits a Presentation to accept a collection of qualified inputs with roles and established correspondence requirements. The current mechanism need not implement that general collection matching, and must not assert that one input is a permanent architectural limit. Lens-specific recommendations can be useful defaults, but should not become exclusive hard-coded Lens-to-Presentation pairings. Existing associated/embedded results remain covered through their actual supplied content contracts. Usage is reporting, outside program Projection semantics. Moving unsuccessful planning reports outside those contracts is the proposed retention change; until accepted, compatibility handling must include the currently retained unsuccessful selections.

## Implementation dependencies to resolve during planning

Focused source inspection against `b8eec90` identified the following planning dependencies, including selector-bearing Projection records. This is not a runtime audit or a complete initiation-attribution trace. These are dependencies to investigate during planning, not contradictions in the adopted architecture.

| Dependency | Planning consequence |
| --- | --- |

## Evidence required from the eventual work

Every existing capability should exercise the proposed request model through its actual execution path. Cover one-shot and shell use, direct session calls, Unicode and JSON output, source-detail and existing pagination inputs, usage and failure reporting. Preserve behavior except for corrections and changes explicitly accepted in the eventual package. The conditional checks below evaluate the preferred design if accepted; they are not instructions to remove current records or compatibility assertions now.

Regression evidence should include:

- F1 descriptions through real publication for all Lens identities and designation modes, using independently stated expectations rather than generating expected prose from the implementation table.
- F2's bind-group, inspect, children/parents refusal, inspect-again journey; existing investigram refusals; unknown prefixes; literal reserved-looking names; mixed and ambiguous matches.
- Planning narrows name lookup using the selected Lens's applicability and supplies only contract-valid subjects to its implementation. Precise incompatible references yield ordinary request outcomes without invoking that implementation; directly supplying invalid subjects to the internal implementation boundary exposes an invariant failure instead.
- Unsettled planning retains accurate resolution and reason information without manufacturing a Projection. Its reporting is distinguishable from valid empty or partial Lens answers and from subsequent evaluation failure. Work already performed for resolution remains accounted for.
- Applicable subjects with partial/unavailable analysis, opaque external dependency subjects, and no hosted invocation on missing/ambiguous or unsupported requests.
- F3 separation across records, Views and observations, with parameters normalized and validated. Current lenses should reject undeclared parameter values rather than silently ignore them.
- F4 selection without an unused retained inspection answer, alongside preservation of legitimate embedded and associated results.
- Stable references and collisions; distinct literal/reference request meanings that resolve to one shared Projection when their qualified answers are otherwise identical; repeat insertion without payload conflicts; retained reconstruction after corrections; operation reuse and attributable qualification. Different captured bases, methods or answer-relevant qualifications must remain distinguishable even when displayed content is equal.
- Both extension walkthroughs, with a reviewable account of additions and evidence that reporting and subject handling work without Lens-specific patches in unrelated layers.
- A mechanical request requiring population discovery, a summary/follow-up using retained operation outcomes, and investigator evidence requests: distinguish the explicit answer from additional request-scoped investigation; preserve initiator and parent/trigger, resource constraints, qualified results and reuse provenance through successful and unresolved outcomes. Identify missing attribution rather than inferring it from command names. No continued work after parent satisfaction/cancellation is authorized by the original request alone.
- Preserve current evaluation retention/retry distinctions: execution-limit stop and investigation failure reuse their retained outcomes; configuration/communication failure can be retried despite a retained unavailable selection. Keep usage independent of acceptance and retain acquired mechanical evidence under its own rules. A no-account result is not automatically a planning failure.
- Every existing program View path uses declared result/Presentation compatibility. Both extension examples reuse a compatible Presentation without a new Lens-name dispatch branch. Incompatible choices yield an intelligible planning outcome, required standard expansions enter Evaluation before arrangement, and empty/partial/unavailable content retains its qualification. A compatible modification to an existing Presentation is verified against its existing uses.

Use existing fixtures, controlled investigator doubles, comparison and publication tests. A live inference run is not needed to verify request integration; interpretation-quality assessment for a genuinely new public Lens would be separate.

<a id="questions-for-independent-review"></a>
## Questions for independent review

Review the proposal's design merits, consistency, completeness and scope before turning it into a formal draft plan. The application specification and corresponding architecture are an adopted baseline, but new and partly untried. Awkward behavior, unnecessary complexity or difficulty preserving useful semantics can justify proposing a revision even without a formal contradiction. Distinguish implementation coupling from architectural problems, explain concrete tradeoffs and alternatives, and identify any governing changes needing human agreement. Do not silently work around the current contracts.

Useful questions include:

- Does replacing addressable unsuccessful selections with interaction-scoped request outcomes preserve enough information and inspectability? Not retaining a plan does not by itself justify removing retained results. Assess the loss of addressability and surviving support/reporting, keeping valid-but-failed or unavailable applications separate.
- Can designation-independent answer identity preserve request provenance, qualified population distinctions and immutable payload consistency across all existing families? Are the decision changes identified precisely enough?
- Do shared resolution, one `inspect` identity and the result/Presentation contracts preserve meaningful differences without unnecessary machinery? Does the distinction between Lens requirements and reusable operations remain usable in both extension walkthroughs?
- What prerequisite-attribution work is necessary for this request-model slice, and what remains independently scoped? Check actual request/evaluation/publication paths, resource limits, cancellation and reuse rather than infer conformance from declarations.
- Does every existing capability exercise the model, with observable corrections for F1–F4 and sufficient mechanical and interpretive extension evidence? Are there hidden dependencies or unjustified exclusions?

These questions are starting points, not an exhaustive checklist. Follow other relevant issues wherever the proposal and governing material lead.

The document review has found no fundamental inconsistency or concrete architectural awkwardness so far. That assessment is limited: source inspection and document/link checks do not replace runtime verification, extension walkthroughs or the prerequisite-attribution trace. Governing material and accepted decisions remain unchanged.

After review and resolution of substantive choices, prepare a formal draft plan and necessary decision proposals. Keep general multi-Projection presentation, captured-basis observation export and retained-Projection redisplay separately tracked unless a concrete dependency warrants an explicit scope change.
