# Implementation Conventions

This document records repeatable application-level engineering practices within PostCode's governing architecture. It is subordinate to the adopted foundation, human-maintained [application specification](app-specification.md), governing core concepts, architectural constraints, accepted decisions, and applicable approved plans. It must not introduce or alter consequential product behavior, conceptual semantics, architectural boundaries, guarantees, or lifecycle policy in place of an accepted decision.

An implementation convention ordinarily describes how the application is written, organized, built, tested, or maintained consistently. A consequential choice about what the system means, preserves, guarantees, depends on, or keeps separate belongs in a [decision record](decisions/). When the classification is unclear, report the question rather than silently establishing a convention.

Agents may update this document only as part of authorized implementation work that establishes or changes the underlying routine practice. Do not change a convention merely to excuse a deviation found in the current work. Record material convention changes in the task record and verify them where applicable. When a convention directly operationalizes an accepted decision, append a short link to that decision enclosed in brackets, as used below.

## Repository layout

- Put application source under `src/`.
- Keep test fixtures under `fixtures/` when they represent repositories or external inputs rather than unit-local test data.
- Keep repository-input fixtures outside the application's compile include list.
- Put build output under the Git-ignored `_build/` directory.
- Use `src/lib/application/index.ts` for direct semantic operations and `application/accounts.ts` for account/provider services. Authentication/help lives in `authentication/commands.ts`; trial rendering lives under `scripts/structured-accounts/support/`. Core must not depend on trial support. Retired shell/worker/observation modules have no compatibility shims. [[Internal application API](decisions/internal-application-api.md)]

- For common contribution history, share only deeply owned immutable content/evidence; capture selection, standing and causes independently for every answer. Keep capture bookkeeping scoped to the owning store/ledger and dispose it on Session close. Frozen external input is not ownership proof. Do not introduce display-time ledger reads or record exposure during capture/arrangement. [[Qualified answers](decisions/qualified-answers-over-contributions.md)]
- Use the common dialog protocol and contribution acceptance for all supported agentic operations. Native evidence records remain qualified provider outputs; legacy tree/correction records, current-primary selection and store-backed presentation binding ports have no compatibility route. Shared hosted transport and usage remain separate from contribution semantics. [[Common contributions](decisions/common-analysis-contributions.md)]

## TypeScript style

- Use strict checking, explicit type-only imports, `.js` relative import specifiers, two-space indentation, single-quoted TypeScript strings, and semicolons.

## Toolchain operation

- Use Node.js 22.13 or later and `tsc` from TypeScript 6.0.3 to build and type-check PostCode. Use ECMAScript modules and npm with a committed lockfile.
- Use Node's built-in test runner and assertions without a separate test framework or transpilation runner. Use npm for installation and build orchestration.
- Install dependencies with `npm ci`.
- One installed TypeScript package currently supplies both the runtime analyzer and the build-time `tsc`, although those roles do not inherently require the same version. Under the current dependency layout, an upgrade made for build-tool convenience also changes the runtime analyzer and must satisfy the semantic verification described under [TypeScript integration](#typescript-integration).

## TypeScript integration

- Use the bundled TypeScript compiler API as the runtime language analyzer. Keep its version pinned because the current slice targets its documented JavaScript API.
- When changing the TypeScript version used by the runtime language analyzer, rerun the semantic fixtures and determine whether any analysis identity method versions must be updated to reflect changed analysis semantics.
- Application modules outside `src/lib/typescript/` must not import the `typescript` package. Interfaces between the TypeScript integration and the rest of the application use PostCode domain types rather than exposing TypeScript compiler nodes, symbols, or other compiler objects. Tests may import the compiler directly when they need to verify the integration against real compiler behavior. [[TypeScript language-integration boundary](decisions/initial-module-inventory-decisions.md#begin-with-a-typescript-module-inventory)]

## Testing and verification

- Test analysis results with small fixtures whose expected answers and limitations are reviewable.
- Include negative and incomplete-analysis cases where they test the epistemological contract.
- Use the real compiler with small fixtures. Synthetic providers are appropriate for evaluation states that the eager first provider does not normally produce.
- Automated tests may create ephemeral test projects through Node's operating-system temporary-directory APIs and must clean them up.
- Test the common contribution mechanism with the controlled producers in `test/contribution-helpers.ts`. They supply uncommon declarations, invalid data and timing; they exercise acceptance, standing and exposure, not the truth of an interpretation. Assert atomic rejection by comparing retained state before and after. [[Common contributions](decisions/common-analysis-contributions.md#production-and-execution)]
- Run `npm run check` to check types without emitting. Run `npm test` to build and execute the tests. Fresh-process tests resolve their own compiled build through `import.meta.url`, rather than assuming a shared checkout build.
- Assert reports in the test body; interaction-driving callbacks capture errors, finish cleanup and rethrow in the test. Register temporary-fixture cleanup immediately after acquisition. Cover Session ownership, validity and finalization through `openApplication`, independently of a host. Test trial rendering against the same supplied structured content for both SVG and text.

## Identity method versions

- When changing analysis, record, handle, or projection semantics, update the responsible identity method version to reflect the change. [[Session context](decisions/transient-analysis-sessions.md#session-as-the-analysis-and-reference-context)]

## Qualified construction and arrangement

- Capture the internal Lens/operation/Presentation catalog before Session opening. Register mechanical constructors with the exact declarations they implement; keep their prerequisite/required expansions and result selection at that registration boundary. New content families add explicit local record, contract and contract handling without Lens-name branches in request coordination. [[Request model](plans/lens-request-model.md)]
- Keep the current module, organization, dependency and investigation core content independent of CLI limits, terminal fitting and format/source choices. Resolve fixed retained references before arrangement; subsequent history changes require another core selection. [[Construction boundary](decisions/qualified-answers-over-contributions.md#qualified-construction-and-retained-support)]
- Supply resolved subjects to family constructors. Retain semantic parameters and complete qualified answer support; keep designation spelling, resolution status and current invocation reporting outside retained answers. Normalize only explicit reference positions in answer keys. Keep consequential lookup context in request delivery independently of answer identity. [[Answer identity](decisions/qualified-construction-under-the-request-model.md#separate-answer-view-and-report-identity)]
- Canonicalize current unordered collection payloads before key construction: selected subjects in evaluation-population order, then outsiders ordered by record ID. Do not apply this policy to meaningful subject order or roles. Ordinary inspection rejects empty resolved input as an invariant violation; legitimate embedded empty module detail uses its explicit internal constructor. [[Unordered collections and embedded detail](decisions/unordered-collection-inspection.md)]
- Pass trial arrangement only selected content and explicit rendering inputs. Do not pass a store, lookup callback or history-refresh closure. Keep each alternative's qualification with its own prose and standalone diagrams. Rendering adds no new program claim. [[CLI retirement](decisions/cli-shell-retirement.md)]
- Preserve selected answer meaning separately from attempt/work/usage reporting; operational reports need no fabricated Projection or View descriptor. [[Identity separation](decisions/qualified-construction-under-the-request-model.md#separate-answer-view-and-report-identity)]

## Selection and session references

- Inspection accepts exact names/generated handles or precise retained same-Session references, retaining every applicable match. Compact alias allocation, lookup and `@` input syntax are removed. Shared request resolution separates precise references from name/handle lookup; core constructors consume settled subjects. [[Session references](decisions/transient-analysis-sessions.md#stable-reference-bindings-within-a-session)]
- Generate mnemonic handles from language names, extensionless basenames, or declared exports, with honest anonymity and explicit provenance. Generic basenames fall back to representative exports. Prefix cues matching `module-` or `group-` plus 8–64 lowercase hexadecimal characters with `handle-`; exact language names remain unchanged. Keep this existing generated-handle method reservation even though compact alias lookup is retired; changing it would change analysis naming semantics.
- Session IDs are random namespaces. Preserve captured input and method support in separate records referenced by provider Claim context; do not use the session identifier as input evidence. Record-key construction normalizes the producing session only in explicitly identified reference positions, using `identityReference`; names, paths, selectors used as literals, prose and captured input values remain unchanged. Foreign references retain their namespace. At mixed reference/literal positions such as selectors, encode a resolved reference as an object distinct from every literal string. This keeps semantic ordering independent of random UUIDs without changing literal evidence. [[Session context](decisions/transient-analysis-sessions.md#session-as-the-analysis-and-reference-context)]
- Resolve precise IDs through actual same-Session records before Lens applicability checks. Preserve supplied spelling in request context and candidate support in qualified refusals; prefix/kind syntax does not prove existence. [[CLI retirement](decisions/cli-shell-retirement.md)]
- Equivalent-run tests preserve every identity/reference relationship, owner, support, qualification and ordering. Control identity allocation where exact equality is needed, or use explicit consistent correspondence. Never strip identities wholesale. Record exact runtime provenance and narrowly enumerated intentional differences.

## Authentication and validation output

- Authentication/help requires no project opening or investigator configuration. Escape terminal controls at inline output boundaries and never print raw credentials or caught provider errors.
- Trial explanation and diagram rendering consumes supplied qualified content. Keep source/evidence literal in structured content; visibly escape controls and XML in rendered artifacts. Each standalone diagram identifies its trial answer, alternative and account item, and states the count, equal standing and unreconciled status of multiple alternatives. Disclosure keeps each alternative's supplied interpretation status and applicable owner limitations separate. Include entry, coverage, applicability and unsupported-content notes in both formats; the SVG explicitly points to its companion text for the full legend. Core state semantics and exact support remain independent of rendering.
- Retired human Views, observation/feedback delivery and disclosure classification do not establish conformance for future interfaces. Record the research-support gap without wiring validation tools to a replacement recording framework.
- Store file associations separately from precise source spans; spans use one-based UTF-16 columns and exclusive ends.

## Accumulation and direct execution

- Test investigator coordination through `test/investigator-double.ts`, replacing only the agent communication participant. Keep real evidence evaluation, acquisition, context delivery and whole-result validation in those tests. Routine tests use no inference credentials. Keep attempt usage outside disposable dialogue state and mark synthetic reports explicitly. [[Investigator execution](decisions/investigator-execution-and-evidence-access.md)]

- Prepare processing indexes over the selected immutable view/evaluation inputs, preserving original ordinals when merging evidence buckets. Artifact/placement indexes use weak capture/layout keys; they do not refresh or cache filesystem observations. Keep ordered export surfaces alongside name lookups.
- Keep Stately imports, encoded topology identifiers and mutable ephemeral graphs inside the directed-graph adapter. PostCode owns selected populations, sorting, all supporting claims and display traversal. Use explicit-direction, membership-checked DFS and sanctioned edge addition for sequential containment acceptance. [[Graph delegation](decisions/graph-kernel-delegation.md)]

- Retain provider discovery and completed work by declared requirements. Keep the module evaluation basis and its expansions together; never broaden projections by selecting the accumulated store indiscriminately. Reuse complete module and expansion outcomes. Reuse partial outcomes only when the provider explicitly supplies a captured `retryBasis` asserting stability until further input acquisition. Validate that basis as analysis inputs in the same session; providers without it still retry. The TypeScript provider keys partial caches by its append-only acquisition revision and reassesses them after dependency input acquisition. Do not add outer module/dependency caches that hide this check. Preserve earlier records when a new input basis permits another attempt. [[Accumulated information](decisions/transient-analysis-sessions.md#immutable-information-within-an-accumulating-session)]
- Evaluators return the immutable store-owned record after insertion. Publish a module outcome and its requested expansion outcomes atomically; a rejected expansion cannot leave a root-only attempt. The store still validates every submitted record and retains existing owned objects after an identical validated resubmission. Provider-owned discovery results are deeply frozen before returning them.
- Pure organization derivations use deterministic record lookup over immutable supporting records, including partial and unavailable outcomes. This differs from provider acquisition/retry rules; repeated derivation cannot refresh a captured basis. Share completed execution/full materialization checks while keeping availability and applicability conditions explicit at each consumer.
- Keep existing claim-context input references when reusing established information. Read first-established support from the stored Claim context. Newly acquired input records support newly established contexts; the store still rejects any conflicting replacement.
- Direct Session callers await opening, execution, validation and close, with asynchronous Git owned in the calling process unless `runGit` is injected. Injecting it leaves subprocess ownership with the caller. First terminal cause is preserved; cleanup/report failures remain separately observable through repeated `interrupt()`/`close()`. Synchronous compiler work/callbacks are cooperative. [[CLI retirement](decisions/cli-shell-retirement.md)] [[Terminal invalidation](decisions/terminal-session-invalidation.md)]
- Snapshot caller output locations into one live exclusion policy shared by compiler and repository acquisition. Re-resolve the captured boundary at each existing validation phase, including missing/dangling targets and aliases; refuse opening when it cannot be established. Retain failed ordinary candidate probes as compiler absence and replay their recovery. Compare missing output suffixes using observed filesystem case handling, without creating probe files or changing stored path spellings. Keep captured source-link resolution separate. [[Generated-output boundaries](decisions/generated-output-boundaries.md)]
- Validate captured compiler probes and repository evidence before and after direct requests. Replay compares against retained observations without extending their identity or acquisition revision. No private publication deferral remains. Client-neutral publication checks separately distinguish withheld output, output failure and post-output invalidation; checks are not atomic or continuous. Detection invalidates rather than refreshes. [[Stable inputs](decisions/transient-analysis-sessions.md#stable-inputs-as-the-session-precondition)]
- Share captured module qualification prose through `qualification-policy.ts`; preserve provider-specific limitations with their support. Human View classification is retired.
- Compare complete qualified content and trial output for ordinary, fresh, follow-up and exact requests. Preserve all evidence, reference relationships, qualification, alternatives, omissions and ordering.
