Date: 2026-09-27 (Europe/London)
Repository baseline: `3415ece523067cc1a06eda42e37bc999ae46c445`

## Findings at a glance

**Pursue terminal layout and standard option parsing as focused early course corrections; consider a focused SCC-library adoption with an explicit maintenance tradeoff.** At this early stage of development, avoiding long-term ownership of generic machinery is a material benefit, even when a migration removes few lines or retains most tests. The recommendations weigh that benefit against migration effort, dependency costs and architectural fit.

Most other apparent infrastructure is either already delegated to Node, Git, or TypeScript, or implements PostCode's evidence and qualification rules. Replacing those rules with framework conventions would move, rather than remove, the work.

The guideline asks for an assessment of suitable libraries and meaningful savings; it does not require a dependency wherever equivalent functionality exists. On this evidence, retaining most of the current implementation is a defensible application of that guideline. This audit cannot establish whether the earlier development process performed the required assessment.

| Area | Recommendation | Likely benefit and limiting factor |
| --- | --- | --- |
| Terminal width and wrapping | **Strongest course-correction candidate** | Prefer `string-width`, probably with `wrap-ansi`, to take responsibility for difficult Unicode layout. Immediate code savings are small; display-column semantics and omission accounting need deliberate integration. |
| CLI argument parsing | **Reasonable course correction** | Prefer Node's `util.parseArgs` for current needs. Commander is an alternative if investing in an expanding command/help interface. Retain PostCode's command semantics. |
| SCCs and graph traversal | **Viable candidates; choose scope and maintenance tradeoff** | `strongly-connected-components` is a focused iterative replacement but dormant; `@statelyai/graph` covers more operations but is young. Both pass deep-graph and compatibility probes. See [graph research](graph-library-research.md). |
| Record validation and storage | **Keep existing code** | Zod can validate shapes, but cannot remove the cross-record, same-session, qualification and atomicity rules. |
| Repository walking, ignore rules and link resolution | **Keep existing code** | Git already supplies ignore decisions. A glob/ignore package would not replace the captured-evidence boundary. |
| Git subprocess handling | **Keep existing code** | Execa/simple-git replace a small invocation wrapper, while byte fidelity, exit classification and capture policy remain. |
| TypeScript analysis and documentation extraction | **Keep direct compiler integration** | TypeScript already supplies the substantial general machinery. ts-morph adds an abstraction without replacing the application semantics. |
| Captured inputs and retained evaluation work | **Keep existing code** | Chokidar is not an equivalent replacement for captured probes; generic caching cannot decide evidence validity. |
| Interactive worker and session control | **Keep existing code** | Piscina supplies pooling and cancellation, but one persistent stateful worker needs little of the pool machinery. |
| Observation batches and local sink | **Keep existing code** | Pino does not replace PostCode's observation model; the actual file sink is about 15 lines. |
| Development measurement and comparison tools | **Keep existing code** | Tinybench supplies benchmarks, not this fresh-process comparison protocol and its rejection/equivalence rules. |

The assessment considers both **retrofitting the present code** and **choosing foundations for continued development**. A preferable starting choice can justify an early migration when it reduces future maintenance obligations. Migration effort and regression risk count; effort already spent writing the existing implementation is sunk cost. Existing behavior tests are migration assets, and keeping them does not count against adoption.

## Preferable starting choices and early course correction

The following choices address which generic responsibilities PostCode should delegate as the application develops. They are based on implementation inspection and package evidence. Graph candidates also have isolated compatibility prototypes; performance and whole-application integration have not been benchmarked or verified.

| Responsibility | Preferred starting choice | Recommendation at the present stage |
| --- | --- | --- |
| Terminal display width | **`string-width`** | Strongest case for changing now. Display width is a complicated generic responsibility, and current character counting is already incomplete. |
| Text wrapping | **Probably `wrap-ansi`** | Evaluate alongside width measurement. Adopt if a small adapter preserves whitespace, continuation markers and disclosure accounting without rebuilding the wrapping engine around it. |
| Standard option parsing | **Node's built-in `util.parseArgs`** | Reasonable correction now. Delegate standard option handling while keeping PostCode's command validation, selector meaning and shell restrictions. |
| Declarative commands and generated usage help | **Commander if investing in an expanding CLI** | Choose it instead of `parseArgs` when its command declarations and generated usage justify the larger abstraction. Do not introduce both as separate parsing layers. |
| Graph algorithms | **`strongly-connected-components` for SCC alone; `@statelyai/graph` for several graph operations** | Both preserve iterative depth robustness in the probes. A focused migration is defensible if dormant upstream maintenance is acceptable; broader adoption trades that concern for Stately’s short track record. |

For terminal layout, the benefit is delegating Unicode display-column measurement and wrapping behavior to established packages. PostCode still owns escaping untrusted controls, deciding what to disclose, counting omitted original characters and preserving source coordinates. The small size of today's implementation does not measure the complexity of making it more complete. See [string-width's API](https://github.com/sindresorhus/string-width#api) and [wrap-ansi's options](https://github.com/chalk/wrap-ansi#api).

For parsing, `util.parseArgs` is the default preference because the current option surface is modest and the application shares parsing between one-shot commands and an interactive shell. Commander becomes preferable when declarative command definitions, validation and generated usage are substantial needs. It supports overriding output and exit behavior, but the adapter must still return PostCode requests and preserve observation recording. See [Node's parsing API](https://nodejs.org/api/util.html#utilparseargsconfig) and [Commander](https://github.com/tj/commander.js).

For graphs, the number of lines understates algorithmic correctness and maintenance obligations. The [graph-library research](graph-library-research.md) identifies two technically suitable iterative candidates. `strongly-connected-components` is the preferred narrow library choice, subject to accepting dormant maintenance; `@statelyai/graph` is the strongest broader candidate, subject to accepting its short track record. Keeping the current implementation remains reasonable if neither tradeoff is acceptable. Neither library popularity nor a short local implementation settles the choice.

Removing migration cost would generally **not** change the choices for the other audited areas: direct TypeScript integration, native workers for one persistent session, Git for effective ignore decisions, and bespoke qualified records, captured evidence and observation batches remain appropriate. Zod would be attractive at a substantial external-data boundary, but that does not make it preferable for the existing relational store checks. Assessing a future external-data boundary is outside this audit's scope.

An early migration should preserve meaningful PostCode semantics without automatically preserving every incidental quirk of the handwritten implementation. For example, supporting standard `--project=value` syntax can be an intentional improvement rather than a reason to add compatibility code. Any such change should be explicit and tested. Stable references, qualification, output safety and observation behavior remain substantive requirements; accidental parser restrictions need separate judgment.

## 1. Terminal text layout — strongest course-correction candidate

**Current implementation.** [presentation.ts:209](../../../../../src/lib/presentation.ts#L209) contains `fitLines` and `wrapText`. Wrapping counts Unicode code points; inventory column sizing/padding uses UTF-16 string length at [presentation.ts:301](../../../../../src/lib/presentation.ts#L301). [organization/presentation.ts:262](../../../../../src/lib/organization/presentation.ts#L262) also sizes columns using string length. Neither count consistently models terminal display columns. For example, a CJK character can occupy two columns while the current wrapping algorithm counts it as one; a base character plus combining mark may occupy one column while counting as two code points. This is a static-analysis finding, not a measured cross-terminal defect.

**Libraries and fitness.** [string-width](https://github.com/sindresorhus/string-width#api) provides display-width measurement, including wide characters and a configurable ambiguous-width convention. [wrap-ansi](https://github.com/chalk/wrap-ansi#api) provides word wrapping with hard-wrap and whitespace options. Both have long publishing histories, very broad npm use, recent releases, MIT licenses and Node requirements below PostCode's floor; see the evidence table. They are good candidates if display-column correctness is wanted. Their purpose is more than replacing a trivial length helper: they avoid growing a bespoke Unicode layout implementation.

**Removable code and tests.** The roughly 14-line body of `wrapText`, plus scattered width calculations, could be replaced or reduced. `fitLines`, disclosure limits, raw-character omission counts, prefixes, continuation markers, tree rows and qualified-view construction stay. Net code reduction may be negligible. No complete existing test should be removed. Keep [cli.test.ts:624](../../../../../test/cli.test.ts#L624), [:686](../../../../../test/cli.test.ts#L686), [:710](../../../../../test/cli.test.ts#L710) and [organization-cli.test.ts:247](../../../../../test/organization-cli.test.ts#L247): they protect unchanged source text, bounded disclosure and terminal safety. A migration would change the width assertion where appropriate and add representative CJK, combining-mark, emoji-sequence and tab cases, without reproducing the library's whole Unicode test suite.

**Integration and migration.** Moderate. Escape repository-derived terminal controls **before** width measurement/wrapping. ANSI-aware rendering must never become permission for untrusted ANSI to pass through. `terminalText` and `inlineText` remain PostCode policy. `wrap-ansi` defaults to soft wrapping and trimming: defaults are not equivalent to the current implementation. Evaluate `hard: true`, whitespace preservation, per-source-line continuation prefixes, CRLF normalization and tabs explicitly. Keep one wrapping policy shared by `fitLines` and rendering so eight-line bounds and omission counts remain truthful. Count omitted original characters separately from display columns. Retain UTF-16 coordinates for source spans. Any changed presentation semantics require the responsible identity-method version review under the implementation conventions.

**Conceptual impact and recommendation.** Low if confined to presentation; material if column counts leak into source positions or raw-character evidence. Pursue `string-width` and probably `wrap-ansi` as an early course correction, preferably coordinated with the UI/UX review. The benefit is more complete display-width handling and reduced future maintenance of Unicode layout. Immediate code deletion is small, and adoption involves a behavior improvement with the integration obligations described above.

## 2. Command-line parsing — reasonable course correction

**Current implementation.** [commands.ts:53](../../../../../src/lib/commands.ts#L53) has `parseCommand`; [commands.ts:90](../../../../../src/lib/commands.ts#L90) has the small `commandWords` tokenizer. The 104-line file also contains a substantial help string. The option scan is about 16 lines; the remaining parser establishes PostCode command validity, defaults, literal selectors, session reference syntax and shell restrictions.

**Libraries and fitness.** [Commander](https://github.com/tj/commander.js) offers declarative commands/options, help generation, output customization and exit interception. Its current release is ESM, has no runtime dependencies, supports PostCode's Node floor, and has extensive adoption and an explicit maintenance policy. [Node `util.parseArgs`](https://nodejs.org/api/util.html#utilparseargsconfig), already available in the supported runtime, is a smaller alternative for the option scan; tokens expose option terminators and argument positions. Neither parses an interactive command string into words.

**Removable code and tests.** `parseArgs` can replace part of the option loop, with a small adapter and semantic checks remaining. Commander could replace the loop and some arity/command checks, roughly 15–30 gross lines, but declarations and error/output mapping may offset the savings. Neither removes the explanatory help prose. Keep [cli.test.ts:108](../../../../../test/cli.test.ts#L108), [:162](../../../../../test/cli.test.ts#L162), [:176](../../../../../test/cli.test.ts#L176) and [shell.test.ts:13](../../../../../test/shell.test.ts#L13). They are CLI compatibility tests, not redundant tests of a generic parser. No whole test is safely removable merely by adopting either parser.

**Integration and migration.** Low-to-moderate for `parseArgs`; moderate for Commander. Preserve returning a `ParsedCommand` instead of exiting or writing directly, reuse across one-shot/shell invocations, explicit option termination, literal `@` selectors, unknown-option behavior, early help handling, error escaping and observation recording. Libraries may accept syntaxes the current scanner does not, such as `--project=value`; explicitly choose compatibility or a documented behavior change. `--` token information must survive parsing because it affects reference interpretation. A Commander adapter must override output and exit behavior. Keep conversion to `ViewRequest` local to PostCode rather than exposing parser objects to the domain.

**Recommendation.** Pursue delegating the standard option scan to `util.parseArgs` as a focused early correction; immediate code savings need not be large to avoid maintaining standard parsing behavior. Prefer Commander instead if the intended CLI development calls for substantial declarative commands and generated usage help. Keep the PostCode semantic layer and literal shell tokenizer.

**Small adjacent exclusion.** [shell-quote](https://github.com/ljharb/shell-quote) is mature, recently published, widely downloaded and MIT licensed, but its variable expansion, operators and comments do not match the deliberately literal tokenizer. Supporting those conventions would change accepted selectors, even though parsing itself does not execute a shell. Keeping the approximately 17-line tokenizer and its tests costs less than adding a compatibility layer. This small utility is excluded from adoption candidates.

## 3. Strongly connected components and graph traversal — viable library choices

**Current implementation.** [dependencies/graph.ts](../../../../../src/lib/dependencies/graph.ts) computes SCCs with iterative Kosaraju traversal, then derives qualified component output. Other candidates include [containment reachability](../../../../../src/lib/repository/layout.ts#L31) and [multi-parent ancestry](../../../../../src/lib/dependencies/organization.ts#L84).

**Libraries and fitness.** The [dedicated graph research](graph-library-research.md) assesses nine choices and identifies two technically suitable iterative implementations. `strongly-connected-components` 1.0.1 is small, MIT licensed, dependency-free and widely distributed, but has no release or default-branch commit since 2014. It is the preferred focused SCC-library choice if dormant maintenance is acceptable. `@statelyai/graph` 2.4.0 is actively developed, has native TypeScript declarations and no mandatory runtime dependencies, and also supplies directed reachability and reverse traversal. Its first npm publication was in February 2026, so it has a much shorter track record.

Both candidates matched an independent correctness oracle for all 65,536 four-node directed graphs and 500 seeded random graphs. They also passed 100,000-node chain/cycle stress tests. Prototype adapters matched full PostCode graph output, including incomplete-root gating and retained claim IDs. Graphlib, Graphology, `@rtsao/scc`, directed-graph-typed and Cytoscape all use recursive SCC traversal and overflowed the call stack on the 20,000-node stress cases. These are environment-specific observations, not minimum failure thresholds or performance results.

**Removable code and tests.** About 30 SCC traversal lines and some adjacency bookkeeping can move upstream. A shared graph adapter might also replace roughly 10–30 traversal lines elsewhere; this is not additive guaranteed savings. Population selection, deterministic ordering, component indices, all original relationship IDs, self-loop classification and the incomplete-evaluation root gate stay. Ancestor claim collection and deterministic refusal of containment cycles stay. Tree rendering bounds, repeated references and omission disclosure are not generic traversal output.

Retain [dependency-projections.test.ts:46](../../../../../test/dependency-projections.test.ts#L46), [:248](../../../../../test/dependency-projections.test.ts#L248), [:260](../../../../../test/dependency-projections.test.ts#L260), [dependency-presentation.test.ts:119](../../../../../test/dependency-presentation.test.ts#L119), [repository.test.ts:256](../../../../../test/repository.test.ts#L256), [:268](../../../../../test/repository.test.ts#L268) and [dependency-projections.test.ts:236](../../../../../test/dependency-projections.test.ts#L236). These test graph meaning and evidence preservation together. No existing standalone generic-algorithm suite can simply be deleted.

**Integration and migration.** A focused SCC adapter has low-to-moderate implementation cost: map sorted project IDs to integer adjacency lists, compute components, map back, and keep PostCode's output assembly. The prototype resolves the depth concern; full application integration remains untested. A broader Stately adoption is moderate work and must justify each additional migrated operation. Create every project node including isolates, exclude external endpoints from SCC computation, retain original relationship IDs, and canonicalize results. Keep multi-parent containment as directed edges; Stately's single-parent hierarchy/LCA conveniences do not implement PostCode's ancestry semantics.

**Recommendation.** An SCC-only course correction using `strongly-connected-components` is defensible if its dormant maintenance posture is acceptable. Select Stately instead when delegating several concrete graph operations justifies a broader, younger dependency. Neither choice authorizes a migration of all graph-shaped domain code or replacement of the canonical program store. See [the research recommendation and verification limits](graph-library-research.md) before choosing scope.

## 4. Runtime record validation and immutable storage — keep

Most of its 350 lines check same-session references, reciprocal entity claims, occurrence partitions, qualified placement outcomes and evaluation prerequisites before atomically publishing a batch. **Library and fitness.** [Zod](https://github.com/colinhacks/zod), with [schema and refinement APIs](https://zod.dev/api), is a mature, heavily adopted, actively published MIT package with no direct runtime dependencies in the inspected release. It is well suited to validating unknown external values and deriving types from schemas. Here the large validation burden is relational, not a handwritten generic JSON-schema engine. Zod refinements could host the same checks, but hosting them does not eliminate them.

**Removable code and tests.** Perhaps 5–15 isolated scalar/shape checks could become schemas; most checks, reference extraction, pending-batch lookup, immutable-collision detection and commit logic remain. Replacing existing domain type declarations with inferred schema types would be a much larger migration, likely increasing code before providing benefits. No tests are removable: retain [records.test.ts:20](../../../../../test/records.test.ts#L20), [:57](../../../../../test/records.test.ts#L57), [:94](../../../../../test/records.test.ts#L94), [:138](../../../../../test/records.test.ts#L138), [organization.test.ts:335](../../../../../test/organization.test.ts#L335) and [dependency-projections.test.ts:275](../../../../../test/dependency-projections.test.ts#L275).

**Integration and migration.** High relative to the removable code. Keep domain types independent of the validator, validate shapes without coercing evidence or stripping meaningful fields, and preserve atomic same-batch references. A schema must not suggest that a structurally valid claim has adequate support. A database or immutable-collection framework would likewise leave the domain checks in place while adding lifecycle/conversion work. Future external investigator responses may justify a boundary schema library, but that is new work outside the existing-code audit. No current storage/schema rewrite is recommended.

## 5. Repository capture, ignore policy and symbolic links — keep

**Current implementation.** [repository/capture.ts:25](../../../../../src/lib/repository/capture.ts#L25) combines Git membership and ignore decisions with filesystem metadata and bounded link resolution; [repository/layout.ts:8](../../../../../src/lib/repository/layout.ts#L8) derives qualified layout. The approximately 321-line capture is substantial, but much of it exists to stop generic filesystem semantics from silently determining domain evidence.

**Libraries and fitness.** [fast-glob](https://github.com/mrmlnc/fast-glob) is an established, broadly used MIT filesystem matcher with synchronous APIs, metadata options and configurable symlink traversal. [ignore](https://github.com/kaelzhang/node-ignore) is a long-established, widely used MIT implementation of ignore-pattern matching with recent publication. Both are good at their stated jobs. Neither supplies PostCode's full Git/evidence contract. The current code does **not** implement a bespoke `.gitignore` parser: it calls `git check-ignore` and captures the applicable policy evidence.

**Removable code and tests.** A walker could displace roughly 10–20 directory enumeration lines, but tracked overrides, per-directory effective policies, local/global exclusions, opaque Gitlinks/nested repositories, byte validation, metadata-only probes and output exclusions remain. Replacing the whole walker would demand hooks and equivalent checks before descent. Pattern matching is already upstream in Git, so `ignore` provides no current parser deletion. No link-resolution test can be removed: generic `realpath` follows live filesystem semantics rather than the captured provider population.

Retain [repository.test.ts:71](../../../../../test/repository.test.ts#L71), [:116](../../../../../test/repository.test.ts#L116), [:153](../../../../../test/repository.test.ts#L153), [:166](../../../../../test/repository.test.ts#L166), [:183](../../../../../test/repository.test.ts#L183), [:201](../../../../../test/repository.test.ts#L201), [:287](../../../../../test/repository.test.ts#L287), [:369](../../../../../test/repository.test.ts#L369), [:424](../../../../../test/repository.test.ts#L424), and the placement/alias cases in [organization.test.ts](../../../../../test/organization.test.ts).

**Integration and migration.** High. Do not traverse ignored/output/opaque regions before deciding they are excluded, silently suppress permission failures, normalize away observed path spelling, or equate unresolved and absent targets. Preserve a broken target versus an existing target whose captured spelling is not established, a proven cycle versus the redirect limit, and tracked membership overriding ignores. A generic glob's results would need explicit deterministic sorting. All these are evidence-boundary responsibilities, not removable library boilerplate. Keep the existing Git-backed capture and bounded resolver.

## 6. Git process execution — keep

**Current implementation.** The `git`/`required` helpers at [capture.ts:41](../../../../../src/lib/repository/capture.ts#L41) wrap `spawnSync` in about 20 lines, with a sanitized environment, byte buffers, a 64 MiB cap, UTF-8 validation and specific status handling.

Either can simplify more elaborate subprocess orchestration; simple-git has raw-command and environment configuration. Its asynchronous API is a poor fit for the current synchronous capture boundary. Execa's synchronous API is closer, but the inspected version brings 12 direct runtime dependencies.

**Removable code and tests.** Only a handful of process invocation/error-plumbing lines are likely to disappear after adapters. Git argument construction, `check-ignore` status 1, config absence, Git-unavailable versus not-in-worktree classification, NUL parsing and evidence checks remain. Keep [repository.test.ts:391](../../../../../test/repository.test.ts#L391), [:424](../../../../../test/repository.test.ts#L424), [:445](../../../../../test/repository.test.ts#L445) and byte/failure probes. No complete test deletion is justified.

**Integration and migration.** Low-to-moderate for Execa, high for making capture asynchronous through simple-git. Preserve raw buffers until UTF-8 validation, significant trailing whitespace, exit/signal distinctions and the existing environment policy; package defaults must be checked explicitly. Translating external errors at this boundary is necessary and consumes much of the potential saving. Revisit only as part of authorized analysis-I/O work supported by measurement.

## 8. Captured inputs, change detection and evaluation caches — keep

**Current implementation.** [typescript/inputs.ts:6](../../../../../src/lib/typescript/inputs.ts#L6) memoizes positive and negative host operations, retains values and replays probes. [project.ts:104](../../../../../src/lib/typescript/project.ts#L104) also checks environment and repository evidence; later code reuses work against captured-input revision. [evaluation.ts:32](../../../../../src/lib/evaluation.ts#L32) preserves attempts and validates retry bases; [session.ts:85](../../../../../src/lib/session.ts#L85) reuses complete qualified outcomes.

**Library and fitness.** [Chokidar](https://github.com/paulmillr/chokidar) is a mature, very widely adopted MIT watcher, with a recent major release and supported Node requirement. It can detect filesystem events; it cannot by itself replace recorded content, absence probes, environment checks or the publication boundary. Adding it could be an optimization signal, not a proof that all relevant inputs remain unchanged. A generic memoizer/eviction cache is likewise not a provider's assurance that partial work is reusable.

**Removable code and tests.** No substantial safe deletion identified. Watching does not remove capture or the basis/qualification checks. Native `Map`/`WeakMap` already supply the generic cache structures. Keep [inputs.test.ts](../../../../../test/inputs.test.ts), [session-inputs.test.ts](../../../../../test/session-inputs.test.ts), [discovery.test.ts:204](../../../../../test/discovery.test.ts#L204), [:223](../../../../../test/discovery.test.ts#L223), [:328](../../../../../test/discovery.test.ts#L328), and the equivalent-session tests.

**Integration and migration.** High. A watcher adds registration races, lifecycle, event normalization and observation-population choices. Replacement risks confusing an event stream with captured evidence, suppressing a valid retry after new acquisition, or erasing prior incomplete outcomes. A future optimization should measure cost and preserve best-effort invalidation semantics. This audit does not propose automatic refresh or a new freshness guarantee.

## 9. Worker RPC and interactive session lifecycle — keep

**Current implementation.** [interactive-session.ts:17](../../../../../src/lib/interactive-session.ts#L17) and [session-worker.ts](../../../../../src/lib/session-worker.ts) use Node workers for one continuing compiler session, one operation in flight, explicit error mapping and termination on interruption. [shell.ts](../../../../../src/lib/shell.ts) already uses Node readline and streams.

**Library and fitness.** [Piscina](https://github.com/piscinajs/piscina) is an established, actively published, broadly adopted MIT worker-pool library. It supports aborting active tasks by stopping their worker. That capability overlaps with current termination, but scheduling many tasks over a pool is not the present requirement.

**Removable code and tests.** Perhaps 15–30 lines of pending-promise/message plumbing could move to a pool adapter. Session opening, retained compiler state, one-operation enforcement, termination state, expected failure translation, parent-owned observations and readline control remain. Net reduction is doubtful. Keep [shell.test.ts:38](../../../../../test/shell.test.ts#L38), [:108](../../../../../test/shell.test.ts#L108), [:128](../../../../../test/shell.test.ts#L128) and [session-inputs.test.ts:293](../../../../../test/session-inputs.test.ts#L293); cancellation and publication are application contracts.

**Integration and migration.** Moderate-to-high. Guarantee worker affinity for the session and prevent replacement workers from continuing under discarded references. ## 11. Development benchmarks, comparisons and test helpers — keep

**Current implementation.** [benchmark-analysis.mjs](../../../../../scripts/benchmark-analysis.mjs) runs paired fresh processes, alternates order, retains warmups/rejected attempts and fails after bounded retries. [measure-analysis.mjs](../../../../../scripts/measure-analysis.mjs) records CPU/wall time, output digests and observations. No substantial net deletion is identified. Keep [benchmark-analysis.test.ts](../../../../../test/benchmark-analysis.test.ts): it tests series completeness after retries, not clock arithmetic. Native `node:test`, assertions, temporary directories and the profiler already supply the generic foundation. No test-framework or fixture-factory migration is justified.

**Integration and migration.** Moderate with no demonstrated payoff. Do not replace the process protocol with an in-process microbenchmark and call the results equivalent. Revisit Tinybench only for a separately useful microbenchmark, not as a retrofit of these tools.

## Small utilities excluded from adoption recommendations

- **Stable serialization:** [identity.ts:26](../../../../../src/lib/identity.ts#L26) has a roughly 10-line canonicalizer. [`fast-json-stable-stringify`](https://github.com/epoberezkin/fast-json-stable-stringify) is mature, very widely used and MIT licensed, but its latest publication is from 2019. The inspected source omits undefined object properties and invokes `toJSON`; PostCode's current routine throws on present undefined values and directly enumerates objects. A drop-in swap is therefore not semantics-preserving. Keep the tiny routine; a migration would need identity/collision and equivalent-run characterization, retaining [records.test.ts](../../../../../test/records.test.ts), [discovery.test.ts:183](../../../../../test/discovery.test.ts#L183) and [session.test.ts:138](../../../../../test/session.test.ts#L138). Do not replace append-only entity bindings with a generic short-ID package.
- **Control escaping:** the seven lines in [terminal-text.ts](../../../../../src/lib/terminal-text.ts) deliberately render controls visibly and distinguish inline from structured text. Stripping ANSI alone would not preserve that policy or cover its bidi/line-control rules. Keep it and the existing output-safety tests.
- **Hashes, UUIDs, paths, dates, cloning, assertions and temporary files:** already use the platform. No evidence justifies a new utility bundle, UUID/date library or filesystem convenience dependency for these calls.
- **Tiny set/map traversals and pluralization:** do not add dependencies individually. Reconsider only as part of a larger, demonstrably useful abstraction such as an adopted graph adapter.
