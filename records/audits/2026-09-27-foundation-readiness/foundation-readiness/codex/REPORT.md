## Overall assessment

**The architectural direction is sound, but the implementation is not yet a sufficiently dependable foundation to extend without a bounded foundation work programme.** Retain the qualified-record model, immutable store, explicit evaluations and projection selections, compiler boundary, Git-backed repository evidence, and separate observation sink. Those are useful working boundaries, not scaffolding to replace. The main weaknesses are at ownership, shared acquisition policy, resource termination, and verification boundaries, with demonstrated unnecessary processing layered on top.

Before extending these patterns to investigation, make tests enforce the claims they appear to make; make retained evaluation ownership and logical publication atomicity consistent; resolve the shared exclusion-policy divergence; and establish truthful cancellation and failed-file cleanup behavior. Correct the generic-responsibility choices early: adopt the selected `@statelyai/graph` direction for concrete current graph operations, delegate standard option scanning to Node, and delegate terminal column measurement. Index selected immutable data rather than repeatedly scanning it. These are recommendations for a young codebase, not rankings based on sunk effort or lines saved.

The review does **not** establish widespread incorrect current CLI output. Several failure findings require controlled invalid inputs or I/O failures, and current projections often reload correct store-owned records. Nor does it certify all language-analysis semantics, cross-platform filesystem behavior, crash durability, or the forthcoming investigator. The existing audits provide substantial verification evidence, but their passing tests and prototypes have limits described below.

### Priority vocabulary

- **Necessary foundation work (N):** repair an existing guarantee or a verification/ownership boundary before building further responsibilities on it.
- **Worthwhile early improvement (E):** a preferable maintained foundation or a demonstrated cost correction; need not block unrelated development.
- **Planned integration prerequisite (P):** needed when implementing the already approved investigation plan, not evidence of an unimplemented current defect.
- **Deferred (D):** insufficient present need for additional machinery.

These categories do not alter the curated backlog. Implementation requires a separately authorized task and any consequential decisions identified here.

## Findings

### F1 — Make equivalence and publication tests capable of rejecting plausible failures (N)

**Classification:** demonstrated test weakness, plus coverage/maintenance concerns. No new production-view defect is inferred from it.

**Evidence.** `test/helpers.ts:21–23` and `scripts/compare-session-requests.mjs:9` replace **every** session-shaped namespace in serialized data with one constant. `scripts/compare-analysis.mjs:30` does the same. The new [probe-results.json](probe-results.json) shows that two different references, one to the correct session and one to another session with the same local suffix, compare equal. It also shows that changing a literal evidence string containing a session-shaped value is erased. The comparisons preserve many relationships, but they do not prove consistent namespace renaming or preservation of all literal content. This is a narrower and more actionable conclusion than discarding the existing equivalence evidence.

The existing sink-assertion defect remains at `test/session-inputs.test.ts:150–155` and `test/shell.test.ts:119–121`: `submitObservation` catches assertion exceptions just like real sink failures (`src/lib/command-execution.ts:14–20`). Prior deliberate-failure copies passed. The ambiguous-navigation test at `test/shell.test.ts:92–101` also asserts in that callback, but its assertions precede scheduling the next input/EOF. **Correction to Claude T1:** failure there can stall the journey and trigger its timeout; it is not established that every such assertion can fail while the test still passes. It still has a poor failure channel and discarded stderr.

**Consequence.** Indexing, graph adoption and identity changes could appear equivalent while losing a reference distinction or altering literal content. A green suite currently overstates particular observation assertions.

**Recommendation.** Use a shared comparison helper that establishes the producing session on each side, validates reference membership and consistent mapping, and renames only identified reference fields and known generated rendering positions. Preserve arbitrary documentation, source excerpts, paths and diagnostic text byte-for-byte. Do not remove relationships, repeated-reference markers, ordering, omissions or qualifications to make equality pass. For rendered strings, use the validated mapping with deliberate handling of generated labels; arbitrary global UUID regex replacement is not enough. Compare structured views **and** output/observation behavior.

Capture batches in test sinks and assert after awaiting the operation; if callbacks drive input, store failures and ensure the driver finishes and rethrows them. Consolidate the repeated CLI invocation/batch-capture helpers in `test/cli.test.ts:15`, `test/organization-cli.test.ts:33` and `test/dependency-presentation.test.ts:13`, with a configurable explicit policy for expected warnings. Keep fixture meaning visible in individual tests.

**Verification for change.** Negative controls must fail for a changed namespace in only one reference, missing edge, swapped evidence, changed qualification, reordered item, dropped repeated marker, changed omission count, and changed UUID-shaped literal text. Positive controls must pass a consistent legitimate renaming. Deliberately falsify each rescued sink expectation and require an assertion failure, not a timeout. Existing retry, collision and cross-session tests remain valuable. Call-count tests should supplement phase-specific publication tests, not substitute for them.

### F2 — Keep namespace normalization out of literal identity data (E; before new interpretation identity)

**Classification:** demonstrated identity-key collision at the generic API boundary; no ordinary current CLI collision reproduced.

**Evidence.** `src/lib/identity.ts:43–46` canonicalizes a key and then performs textual `replaceAll(session, 'session')`. In the new probe, `recordId(s, 'example', {text: s})` equals `recordId(s, 'example', {text: 'session'})`. Distinct literal content is collapsed because reference spelling and data are not distinguished. The immutable store would reject two conflicting records under that key rather than silently overwrite them. Current compiler inputs are unlikely to contain their randomly generated namespace, which limits current impact; forthcoming interpretation may include actual references in prose.

**Consequence.** Identity correctness depends on incidental restrictions on string contents. Broadening record producers without addressing that assumption creates avoidable collision/failure cases.

**Recommendation.** Retain PostCode-owned identity policy and native hashing, but make local reference identity explicit in key construction. Normalize known reference positions or use explicitly constructed local-key structures; do not rewrite arbitrary serialized strings. Keep the small canonicalizer for its intended plain-data domain rather than adopting a generic stable stringifier with different undefined/`toJSON` behavior. Do not call this implementation RFC 8785 compliant without defining and testing its accepted value domain; it is not a general validator for arbitrary objects.

**Decision/verification.** This changes key semantics and requires responsible identity-method version review; it is separate from a semantics-preserving performance task. Test literal namespace text, actual same-session references, foreign references, consistent equivalent runs, stable within-session compact bindings and collision rejection. Do not normalize away this difference in tests. This is a focused identity-boundary improvement, not a new identity framework.

### F3 — Make the store the authority for retained evaluation results and coupled publication (N)

**Classification:** demonstrated mutable-ownership weakness (existing probe) and demonstrated split-publication weakness under controlled invalid expansion input (new probe).

**Evidence.** `src/lib/evaluation.ts:30–60` caches the original shallowly assembled outcome after the store has cloned it. The prior state probe changed a producer array: stored modules stayed at one, cached modules became zero, and the projection remained correct because it reloaded the stored evaluation. That contradicts the unqualified claim in Claude S1 that all cache state is conformant. `src/lib/dependencies/evaluate.ts:14–24` likewise returns a producer-derived outcome after storage, though it does not install the same cache.

The root evaluation and expansion outcomes are inserted in two `put` calls (`evaluation.ts:50–54`). The new probe supplies an expansion with a nonexistent claim. The second batch rejects, but one root attempt remains; the next valid attempt is numbered 2. This is an invariant-failure path, not a demonstrated error from today's TypeScript provider. The store's own batch atomicity is working correctly.

**Consequence.** Consumers must remember which return values are store-owned and which are producer aliases. More providers and retained result types would spread that fragile convention. Atomic storage alone does not make a sequence of storage calls atomic.

**Recommendation.** Cache IDs or store-owned immutable records; return the stored outcome after successful insertion. Construct the coupled root/expansion outcome batch before one `put`. Preserve independently acquired evidence and explicitly partial **valid** outcomes; do not turn this into an all-session rollback mechanism. Apply the same ownership rule at other evaluation return boundaries as they are touched. Retain the existing clone, freeze, collision and cross-record validation boundary.

Caches of deterministic organization results should hold immutable records/IDs too. The provider's `support` map (`typescript/project.ts:182,333–341`) preserves first-established context support, which is historical evidence rather than a cache to update to the latest input. It need not be removed merely because the store also contains that field. A new store `has` API solely to eliminate a sound private map is optional, not necessary foundation work.

**Verification.** Mutate producer-owned nested arrays and objects after recording; initial and reused returns must agree with `store.get(id)`. Reject one expansion in a multi-record batch and check every coupled outcome is absent, previously accepted evidence is unchanged, and subsequent valid recording works. Existing `test/records.test.ts:138` covers only store copying; keep it and add evaluation-boundary coverage. These strengthen existing contracts without redefining partial-result semantics.

### F4 — Establish one generated-output policy, with separate live resolution and captured link semantics (N/P)

**Classification:** demonstrated policy divergence; structural concern that becomes an immediate investigation integration risk.

**Evidence.** `src/lib/typescript/inputs.ts:8–34` and `src/lib/repository/capture.ts:107–124` independently resolve exclusions. The former climbs using following existence checks; the latter can resolve a dangling link through `lstat`/`readlink`. The prior reproduced `out -> elsewhere/target` case records different real exclusion paths. Subsequent target creation invalidated compiler inputs in that experiment, so it did **not** demonstrate ordinary silent contamination. That fail-safe case does not make the policy duplication appropriate. Lexical containment is also duplicated (`capture.ts:19`, `inputs.ts:24`, `organization/placement.ts:11`).

**Consequence.** A third content reader for investigation could select another interpretation of the same output boundary. Performance maps based on inconsistent path meanings would make the divergence less visible, not fix it.

**Recommendation.** Define a small shared acquisition/output-policy component that owns normalized lexical/resolved exclusion pairs, unresolved/error states, matching, and boundary revalidation. Snapshot caller options at opening. Resolve the policy before relevant reads, use the same policy in compiler and repository acquisition, and register new acquisitions with the session's validity machinery. Retain the distinction between an exclusion path resolved against the live filesystem and an ordinary source link resolved only through captured visible repository evidence. **Do not merge those two resolvers** or replace apparent-path module identity with realpath identity.

For dangling and cyclic exclusions, explicitly choose conservative resolution or explicit unavailability/refusal. A cross-check test alone is insufficient if two implementations remain authoritative and are knowingly different. Share the ordinary platform-path containment predicate where semantics are identical, but retain POSIX repository-relative paths, apparent paths, case/precomposition policy, and captured provider boundaries as distinct concerns.

**Decision/verification.** Resolving differing exclusion semantics requires an explicit policy choice; any altered captured identity/input method needs a version review. Test lexical and real aliases, missing descendants, dangling targets created later, retargeting, cycles, output inside an ignore-policy path, paths outside the worktree, conventional `_build`/`_observations` names that were not supplied, and duplicate/reordered exclusions. Assert both recorded policies and actual filtering. Keep the existing 40/41-redirect and apparent-identity tests. New content acquisition must neither read excluded content nor claim that a previously unobserved file had its later contents at opening.

### F5 — Bound Git lifetime honestly and make worker coordination failure-safe (N/P)

**Classification:** demonstrated cancellation limitation and failed-send state defect; unresolved execution-policy choice.

**Evidence.** `repository/capture.ts:44–55` uses synchronous child processes without timeout. `interactive-session.ts:56–64` rejects the request immediately but awaits worker termination; `shell.ts:84–87` awaits that cleanup. Existing controlled children delayed termination by three and six seconds. The new [timeout-results.json](timeout-results.json) shows a **500 ms** `spawnSync` timeout returning after **1,331 ms**, when a child that handled SIGTERM exited voluntarily. No infinite child was launched. Node documents that synchronous calls wait for actual exit even after the timeout signal. [Node 22 child-process documentation](https://nodejs.org/download/release/v22.13.1/docs/api/child_process.html#child_processspawnsynccommand-args-options).

Thus “add a timeout and cleanup is bounded” is too strong unless the signal/child behavior and platform limits are accounted for. A per-call timeout also does not cap the number of sequential Git calls or slow filesystem operations in a capture.

`interactive-session.ts:37–45` installs pending state before `postMessage`; the prior real `DataCloneError` probe left a phantom concurrent operation and an unhandled rejection on close. Current parsed shell requests are cloneable, limiting exposure. The unused worker-side `close` message (`session-worker.ts:15`) is not a functioning graceful-shutdown contract.

**Recommendation.** First give subprocess execution an explicit owner, deadline policy, operational-failure mapping and cleanup tests. A deliberate hard signal for owned Git children can mitigate stalled ordinary children on supported platforms, but cannot promise prompt cancellation of all native I/O or descendants. For prompt cancellation through Git, prefer a cancellable asynchronous child owner or supervised process boundary; do not detach the wait and call that cleanup. Do not change repository evidence semantics merely to fit a process package. Native Node remains a suitable mechanism; a pool/RPC framework does not solve session ownership or these termination semantics.

On synchronous send failure, clear/settle pending state exactly once, consume the promise rejection, and explicitly choose reusable-versus-terminal session behavior. Remove unused close protocol only after confirming termination remains the intended disposal mechanism. Put reusable error/request contracts in a neutral execution boundary when separating coordination; production publication should not need to import worker construction just to name interruption.

**Verification/decision.** Use readiness handshakes, outer watchdogs and unconditional cleanup. Cover cancellation during opening, compiler work, Git validation, before publication, and after output; assert actual worker/child exit and retained actual-output observations separately from promise rejection. Exercise unexpected exit, open failure, synchronous send failure, close while pending, late replies and concurrency refusal. Register cleanup immediately after worker/fixture acquisition in `scripts/compare-session-requests.mjs:23–26,44` and affected session tests; attempt independent cleanups independently. The previous native interruption probe's phase marker is overwritten by validation reads, so its failing control cannot certify cancellation. Repair that harness before relying on it.

The human needs a documented acceptable cancellation/deadline policy and supported-platform limits. Do not silently promise instantaneous cancellation, automatic worker restart, or continuation under discarded references. These choices should be coordinated with planned asynchronous investigation, whose guard explicitly admits in-flight cancellation limitations.

### F6 — Own failed observation files without inventing a durability contract (N; stronger durability D/decision)

**Classification:** demonstrated incomplete-file residue under injected partial-write failure; maintenance and contract-clarity opportunity.

**Evidence.** `src/lib/observations.ts:57–64` writes directly under the final name using `wx`. The previous short-write/ENOSPC probe left nine bytes of malformed JSON. `command-execution.ts:14–20` correctly warns while preserving a successful view. No current archive consumer or real disk exhaustion was demonstrated.

**Recommendation.** Preserve the simple native file sink and application-owned batches. Connect exclusive creation, handle ownership, close and deletion of **only the newly created incomplete file**. Failure on `EEXIST` must not remove a prior batch. Alternatively stage privately and publish a complete file with no-overwrite semantics. Plain `rename(temp, destination)` may overwrite a destination and is not automatically equivalent to `wx`. Temporary-plus-rename alone also does not establish power-loss durability.

**Decision.** Ordinary exception cleanup strengthens the current implementation. Atomic visibility during process death, persistence after OS/power failure, staging scavenging, fsync policy, deduplication and historical retention are distinct sink policies. Do not add them implicitly or reinterpret `accepted: true` as a crash-durability guarantee. The accepted observation decision leaves durability to the sink; no producer-side retry queue or logging framework is needed for this correction.

**Verification.** Fail before creation, after a short write, on close/publication and on cleanup; preserve an existing destination and private modes. Verify rejected/throwing sinks cannot erase produced output or turn a successful view into failure. Test the real sink alongside abstract sinks, and keep observation delivery outside disposable worker state. Report any stronger crash behavior separately from exception tests.

### F7 — Adopt Stately across concrete graph kernels, retaining domain graph policy (E)

**Classification:** maintenance opportunity and bounded tested integration direction; concrete adapter mismatches, no blocking semantic incompatibility found.

The human has selected **`@statelyai/graph`**. This review does not reopen that selection or recommend the earlier SCC-only package. Version **2.4.0** is the assessed published source, not an instruction to float to latest. It is MIT, has no mandatory runtime dependencies, and its optional format/layout/schema peers are unnecessary here. The earlier metadata indicates a short publishing history; retain a pinned version and deliberate upgrades with compatibility checks. Upstream primary documentation describes plain graph objects, mutations and optional adapters. [Stately documentation](https://github.com/statelyai/graph).

Existing SCC research already compared an independent reachability oracle on all 65,536 four-vertex directed graphs, full qualified assembly on 506 cases, strict TypeScript adapters, and 100,000-node chains/cycles. Those results were read and reused, not rerun. Published 2.4.0 source was inspected directly; this review adds the missing **incremental layout adapter** and indexed all-edge ancestry experiment.

| SCC partitioning, `dependencies/graph.ts:6–43` | Delegate SCC. Include every project module/isolate; filter external endpoints; canonicalize sorted members and component order. Retain original relationship IDs, parallel claims, self-loop cyclic flags, sorted condensation children and `rootsEstablished` gating in PostCode (`:44–61`). Do not use library source-node detection to establish roots of incomplete evidence. |

| Multi-parent ancestry, `dependencies/organization.ts:84–107` | Delegate incoming reachability, including self. **Concrete mismatches and obligations.**

1. Repository root path is the empty string. `createGraph` rejects it as a node ID. The first prototype failed on exactly this input; [root-id-failure.log](root-id-failure.log) is retained. Prefix-encoding internal region IDs resolves it without changing domain paths. Nonempty stored `RecordId`s need no such path encoding.
2. Library indices are derived state. Published `indexing-CcJvYaxT.mjs:1–64` caches by graph identity, array identity/count and explicit mutation notification. Direct endpoint-field mutation can leave adjacency stale; the new probe demonstrates it and verifies explicit invalidation. Own one ephemeral graph inside the adapter; build once for immutable record selections, and use documented mutators for sequential layout construction. Do not pass a mutable graph through the domain store or mutate shared record objects.
3. `hasPath(g, 'absent', 'absent')` returns true in the inspected release. Validate node membership at the adapter boundary; current layout already checks region membership. Its implementation also uses `queue.shift()`. Prefer a short-circuit explicit-direction `genDFS` traversal for this reachability adapter; do not claim an unmeasured speedup or an unconditional linear-cost guarantee for `hasPath`.
4. Traversal order is not PostCode ordering. Retain explicit sorting and original-order merging where evidence order matters. Upward graph edges are ordinary directed relationships, not library `parentId` hierarchy: PostCode allows multiple parents.

**New verification.** [layout-prototype.mjs](layout-prototype.mjs) replaces only the existing layout reachability kernel in a disposable compiled copy and uses prefixed IDs plus `addEdge`. It matches **128 complete layout results** (64 combinations of cross-directory links, both original/reversed artifact order), including self/cyclic and broken-link outcomes. A diamond with two parallel supporting claims preserves all five claims using incoming traversal plus indexed incoming edges. These are isolated JavaScript prototypes, not a production integration, strict-type validation of these new adapters, or a performance benchmark. Earlier SCC depth/type evidence does not certify all other APIs.

**Verification for adoption.** Retain existing known-answer SCC/isolate/self-loop, incomplete-root, multi-parent and deterministic-link tests; add durable adapter tests for root encoding, membership, incremental mutation, all supporting claims and input permutations. Verify full qualified views with F1's strengthened comparator. Do not add a broad graph abstraction, graph database, format adapters or generic path enumeration. Planned citation reconsideration will require per-correction exemption-aware traversal; plain transitive reachability over all citations would be semantically wrong. Build that policy when the plan implements it.

### F8 — Index selected immutable bases and reuse pure results, without bypassing acquisition (E)

**Classification:** demonstrated inefficiencies from both processing audits, with supplementary ownership/key requirements.

**Evidence.** `composition-view.ts:10–25` scans all expansion claims/outcomes for each displayed module; `presentation.ts:82,114–148`, `organization/presentation.ts:114–145` and `dependencies/presentation.ts:95–147` add repeated joins. `organization/placement.ts:23–33` repeatedly searches capture/layout arrays; provider materialization groups by repeated filtering (`typescript/expansions.ts:286–301`, `typescript/project.ts:313–315`). `session.ts:85–110` caches only full organization outcomes, although immutable outside-organization endpoints can make pure relationship organization partial forever. All were checked in current source; earlier measured costs were not repeated.

**Recommendation.** Adopt a local prepared-index idiom: index **projection-selected** claims/outcomes once per view, retaining established ordering and qualifications. Share composition preparation across its three callers. Build placement lookup maps per immutable repository/layout pair. Preserve the locator's boundary checks, longest-prefix rules, apparent path semantics and 40/41 redirect behavior. Claude's ancestor-walking prototype is evidence for a possible simplification, not a reason to bypass those checks. Keep copied/constructed maps privately owned.

Reuse pure organization derivations even when their answer is partial/unavailable, using full basis keys: module evaluation plus requested group expansions; dependency evaluation plus organization evaluation. Qualification is not the same as retryability. Continue entering the provider/evaluation boundary so acquisition-revision and `retryBasis` rules run. A path alone, session alone, current store size, or “last dependency result” is not a sufficient key. Preserve earlier results and first-established supporting inputs.

Export-surface name maps (`typescript/expansions.ts:43,66,102,199`) and per-captured-span excerpt reuse (`typescript/project.ts:239–247`) are worthwhile bounded follow-ons. The former has demonstrated quadratic comparisons; the latter has measured allocation cost. Neither justifies route-path enumeration or process-global filesystem caches.

**Verification.** First apply F3's ownership rule and F1's comparisons. Count store reads/lookups at two representative sizes rather than asserting narrow timing thresholds. Test ambiguous names, shared origin/alias documentation, collapsed external qualifications, source details, partial/unavailable bases, and an actually different basis triggering recomputation. Preserve record/evidence order when merging index buckets. Reuse the existing prototype only after these checks; its 186 comparisons were rendered-output comparisons, not every structured Unicode view field, and cannot certify all unseen states.

No identity bump is needed for genuinely unchanged semantics; changes in ordering, selected evidence or omission meaning are not incidental performance changes. Store-wide evaluation indexing, all-pairs ancestry caches and persistent caches remain conditional on history/profile evidence. Per-view maps, provider-preparation maps and per-evaluation graphs have clear disposal points; a universal cache framework would obscure them.

### F9 — Improve input validation cost without silently changing coverage or publication phases (E; coverage/frequency decision)

**Classification:** demonstrated cost from earlier measurements; policy and verification concern.

**Evidence.** `typescript/project.ts:104–108` checks environment, captured compiler probes and full repository recapture; `typescript/inputs.ts:64–73` replays positive/negative observations. `session.ts:66–75` checks before and after direct execution; `publishCommand` requests deferred checking and checks after result delivery before output and again after output (`command-execution.ts:32–36`). `test/session-inputs.test.ts:263–291` asserts two/three source reads, while `:293–326` tests actual worker-delivery timing. The count check is useful but not proof that checks cover the right inputs at the right phases.

**Material clarification.** The accepted stable-input decision explicitly says detection strategy/coverage are implementation choices, and that revalidating every captured input is **not a required mechanism** (`docs/decisions/transient-analysis-sessions.md:185–224`). Current conventions and CLI documentation do commit to concrete pre/post-publication behavior. It is therefore too strong to say every internal validation optimization necessarily changes the governing contract; it is also wrong to treat documented checks as disposable. A reduction in coverage/frequency must be proposed with its changed behavior and receive human direction, with a decision record if it changes consequential guarantees. Do not silently edit conventions to justify it.

**Recommendation.** Preserve present phases initially. Cache the canonical representation of the retained repository snapshot, compare primitive captured values directly before structural canonicalization, and profile live recapture/probe replay independently. These are local opportunities, not newly measured speedups. A watcher or metadata-only check cannot establish the same content/negative-probe coverage by itself. Shared exclusion ownership (F4) precedes broader change detection, and new investigation acquisitions must extend the captured probe population.

**Verification.** A coverage matrix should distinguish source/config content changes, deleted/appearing resolution candidates, directory membership, Git ignore/tracked/link changes, environment changes, output retargeting and operational verification failure. Exercise a change between worker response and output as well as after output, and assert invalidation latches. Do not refresh earlier evidence. Explicitly retain non-atomic/first-observed limitations. Assess actual post-optimization CLI cost separately from in-process view-stage measurements.

### F10 — Delegate terminal measurement and option syntax, with deliberate presentation semantics (E)

**Classification:** implementation/maintenance opportunity, demonstrated candidate semantic differences; terminal column limitation established from code and library probes, not physical-terminal measurements.

**Terminal layout.** `presentation.ts:78–80,209–235,301` truncates/wraps by code point and sizes columns by UTF-16 length; `organization/presentation.ts:262` also pads by length. Published **string-width 8.3.0** and **wrap-ansi 10.0.2** were fetched into this directory, source-inspected and exercised with their actual dependencies. `wrap-ansi` hard wrapping is grapheme-aware, so rejecting it simply because PostCode emits no styling is insufficient. However, it performs unconditional Unicode normalization: the new probe verifies `e` + combining acute becomes precomposed `é`, even without a line break. It also expands tabs; escaping first avoids passing raw terminal controls. Its defaults trim and soft-wrap; they are not current policy. A two-column grapheme in one available column still exceeds that width rather than splitting. See [terminal-results.json](terminal-results.json), [published archives/hashes](upstream/metadata.json), [width API](https://github.com/sindresorhus/string-width#api) and [wrapping API](https://github.com/chalk/wrap-ansi#api).

**Recommendation and decision.** Adopt width measurement now. Prefer library wrapping if the human accepts canonical-equivalent normalization in rendered text and a small adapter meets the whitespace/continuation contract. Apply it after escaping and per logical line, then add PostCode prefixes. If exact code-point preservation is required, the assessed `wrap-ansi` API has no normalization-disable option: retain the small local break/indent orchestration over library widths and platform graphemes, or investigate another wrapping library. This is a concrete semantic reason to retain orchestration, not a migration-cost objection. Do not fork hundreds of lines of ANSI machinery merely to remove normalization.

Keep omission counts in original code points unless deliberately changed; selecting grapheme-safe prefixes does not require changing that unit. Use one layout calculation for fitting and rendering so height bounds remain truthful. Choose ambiguous-width convention and indivisible-wide-cluster behavior explicitly. Presentation changes require responsible method-version review; JSON/domain text must remain unchanged unless a separate contract change is intended. Test CJK, decomposed characters, emoji ZWJ, combining marks, tabs, CRLF, controls, prefixes, continuation lines, narrow budgets, exact omissions and source coordinates. Existing ASCII length assertions must become independent display-width/grapheme checks. These probes do not certify terminal-specific rendering or full integration.

Keep lens/arity validation, shell project restrictions, selector/ref semantics, help prose, controlled errors and publication in PostCode. The new runtime matrix confirms important deltas: `--project=value` becomes accepted; `--project -x` is rejected by strict parsing whereas current code accepts it; `inspect -x` is currently a positional selector but becomes an unknown option; early `--help --unknown` currently succeeds but a full strict parse rejects it. Tokens preserve `--`, which is necessary to keep literal `@` selection distinct. [Node 22 parseArgs documentation](https://nodejs.org/download/release/v22.13.1/docs/api/util.html#utilparseargsconfig).

Test one-shot and interactive paths, repeated options, empty values, option-looking names, `--`, literal `@`, ambiguous matches, and usage/refusal observations. Commander is a reasonable later alternative if declarative command/help maintenance becomes substantial; do not adopt two option parsers or a framework merely in anticipation of more commands.
