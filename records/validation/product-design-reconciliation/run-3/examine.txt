The earlier account is accurate, but the implementation has two material coordination limits beyond its sequential hit/miss description. First, `lookup` caches completed values but does not record work in progress, so overlapping misses are not combined: each can start its own remote read, and completion order—not invocation order—determines which single entry remains cached. A value cached under one adapter can therefore continue to satisfy the same key after `configureAdapter` selects another adapter. @investigram-96240a19 · interpretation

For the same key, this can duplicate remote work and each caller receives the result of its own read. Thus the cache state after overlap follows completion order, while each call's returned value remains independent of the entry left behind.
