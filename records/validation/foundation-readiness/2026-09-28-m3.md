# Foundation readiness M3 validation

Checkpoint: acquisition, execution lifetime and local observation publication.
This is implementation-agent evidence for the intermediate review, not independent
acceptance or completion of the foundation-readiness plan. The task remains active.

## Scope and method assessment

Packages 4–5 are implemented under the accepted output-boundary, execution-ownership
and local-observation-acceptance decisions. M2 was accepted by the human after two
review rounds; its disposition and the task follow-up preserve that decision.

Compiler and repository acquisition now use the same captured live exclusion
policy. Caller options are copied before asynchronous opening. Lexical locations
and resolved locations are retained; aliases count once, missing suffixes and
dangling targets remain enforceable, and cyclic/unverifiable explicit boundaries
refuse opening before compiler acquisition. Native realpath handles existing paths
and filesystem spelling; component resolution handles missing/dangling targets,
including nested symbolic links before `..`. Boundary replay can invalidate but
never silently refresh the retained basis. Captured repository source links keep
their own resolver and apparent path semantics.

`postcode/observed-inputs@3` advances to `@4` for the changed compiler exclusion
resolution policy. `postcode/repository-inputs@3` advances to `@4` for shared
boundary acquisition and the explicit stable timeout qualification. No record,
projection, presentation or observation schema version changes in M3. The M2
reference corrections and primary-producer qualification policy remain intact.

Both CLI entry paths now put compiler work in the private worker. The parent owns
Git handles and exit monitoring, observation delivery, operation identities and
worker disposal. Direct sessions use the same Git owner in the calling process;
opening, execution, checks and close are awaited by their callers. Direct compiler
work remains synchronous in that calling process; using the CLI worker boundary is
what makes native compiler work independently disposable. The compiled private
worker does not inherit parent launch flags such as `--input-type` or `--expose-gc`.

The current two direct-execution checks and three CLI publication checks remain.
Retained repository serialization is computed once; primitive compiler probe values
compare directly, while structured values retain canonical comparison. No replay
phase or negative-resolution coverage is removed. Ignored-directory ancestry uses
a capture-local membership set and parent walk, preserving tracked overrides.

## Limits and their meaning

| Limit | Selected value and rationale |
| --- | --- |
| One Git invocation | 30 seconds. Generous relative to the exercised small and generated repositories; bounds a stuck acquisition without imposing an analysis-wide latency threshold. It is not an aggregate budget across Git calls. Larger valid work can still time out and is qualified honestly. |
| Graceful termination | 250 ms before forced termination. Gives an ordinary local child a short cleanup opportunity without making interactive interruption wait for the whole Git deadline. Native tests also exercise a child that handles SIGTERM and requires SIGKILL. |
| Cleanup reporting | 2 seconds from cancellation for each owned resource. Bounds the cleanup report, not OS process lifetime. Failure names the unconfirmed child/worker; exit monitoring and ownership remain active. |
| Git output | 64 MiB combined stdout/stderr. A bounded owner replaces synchronous buffered execution and retains UTF-8 checks at the repository boundary. |

POSIX cancellation requests SIGTERM followed by SIGKILL. The Windows branch requests
forced termination directly, but was not natively verified. Child-handle signalling
does not establish descendant-tree ownership or termination. Native filesystem or
compiler work can have platform limits; no whole-analysis deadline or universal exit
guarantee is claimed.

A confirmed opening Git timeout yields unavailable evidence with operation/code,
not an empty repository. Consistently unavailable capture remains qualified;
recovery or loss changes the basis and invalidates. Unconfirmed opening cleanup
is a resource failure. During later checks, unconfirmed cleanup invalidates the
unverifiable basis; closing the owner reports its resource cleanup failure
separately. Interruption remains status 130 even when cleanup reports failure.

## Observation organization and acceptance

New batches use `<project-label>-<six-hex-key>/YYYY-MM-DD/HH-mm-ss.sssZ_<uuid>.json`
beneath the existing observation root. The label derives from the configuration
directory basename, with NFKD normalization, ASCII-safe substitution, edge-hyphen
trimming, a 64-character limit, lowercase and `project` fallback. The key hashes
the normalized absolute configuration path. This requires no extra source read or
project registry and supplies grouping even for a batch without a view. The suffix
is a compact disambiguator, not a collision-free domain identity.

One UTC submission time chooses date and time. Each attempt exclusively creates a
private same-directory staging file, writes and closes it, creates a final hard
link without replacement, then unlinks staging. Successful link creation commits
acceptance. Later staging cleanup failure warns of an accepted publication; it does
not produce a false observation gap or retry. Only staging owned by the attempt is
removed. New directories use 0700 and files 0600; existing permissions remain intact.
The generic sink interface and format-version-1 batch schema remain unchanged.

The local sink's additional cleanup-warning acknowledgement is interpreted by the
publisher outside its sink-rejection catch. The complete observation root stays
excluded. No migration, historical reader, automatic scavenging, overwrite fallback,
or power-loss persistence guarantee is introduced. Hard kill can leave staging.
