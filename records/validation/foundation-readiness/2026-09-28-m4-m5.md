## Index ownership and semantic changes

Composition, documentation, exports, qualifications, group membership, relationship
organization and source-detail indexes are built from the selected immutable
view/evaluation inputs. Bucket merges use original ordinals where order matters.
Artifact/path lookup uses weak capture/layout pair keys and segment ancestors; it
preserves apparent paths, opaque boundaries, longest matching link, cycles and the
40-redirect limit. No index performs filesystem acquisition or bypasses validation.
Provider export arrays retain their order alongside first-match name maps. Source
excerpt counting scans original code points without allocating a whole-span array;
captured text bounds and UTF-16 positions remain unchanged.

Deterministic operation guards cover two sizes each. Repeated placement queries
over 64 and 512 artifacts read artifact paths at most twice per artifact across
index preparation and both query passes. Composition preparation for 32 and 256
modules reads at most five records per module; both subsequent query passes read
zero additional records. These are operation assertions, not latency thresholds.

`postcode/presentation@25` advances to `@26` for intentional terminal changes:
display-cell width, grapheme-safe wrapping/truncation, narrow ambiguous characters,
visible tabs, escaped CR (including CRLF), structured LF and indivisible escape
tokens. Fit checks and actual rendering share the calculation. Omission counts
refer to original code points, including controls, and oversized indivisible text
is disclosed. JSON text and stored source evidence/UTF-16 coordinates retain their
previous policies. Grapheme segmentation does not normalize source spelling.

Strict `util.parseArgs` scanning accepts inline project paths, requires inline
dash-prefixed values, rejects duplicate/empty project values, and parses all
options before help. Help bypasses operand validation only; it cannot bypass a
scanner error or the shell's project restriction. Boolean repeats are idempotent;
`--` retains option-like and literal `@` selectors. Controlled scanner diagnostics
now use Node's wording, including capitalized `Unknown option`. No domain method
version is changed for invocation scanning, and observation schemas are unchanged.

Unit and end-to-end checks cover the grammar in both interfaces, quotes and literal
selectors, no one-shot observations on scanner refusal/help, shell refusal
observations, and a successful subsequent command. Terminal checks include CJK,
combining sequences (also on an escape's final character), ZWJ emoji, tabs, CRLF,
controls, narrow budgets, continuation prefixes, exact omissions and stored source
positions. Existing source-detail and assertion-height fixtures remain active.

## Integrated measurements

The [driver](m4-measurements.mjs), [conditions](m4-measurements/conditions.json),
[summary](m4-measurements/summary.json) and adjacent raw reports retain both build
identities. The timing baseline is accepted M3, not the original pre-plan program.
The after build contains all eight packages. No gains from earlier experiments
are added to these measured results.

Each fixture has 80 modules forming a broad wildcard-export chain and 24 artifact
groups. The two sizes contain 240 and 2,400 non-module artifacts. Two repetitions
alternate before/after order. Runs were sequential after verification completed,
with naturally warm filesystem caches; reports retain runtime/CPU/load/memory
conditions. The extra artifact count is included in opening and every repository
validation pass, rather than being excluded from the input population.

Direct request timing includes its two validation passes and excludes the separately
timed check immediately afterward. That extra check estimates a pass's cost; it is
not a measured subtraction from request time. Interactive timing includes the three
CLI checks and worker/prompt delivery through a no-op sink. Full CLI samples use a
fresh Node process, hash stdout instead of terminal I/O, and publish actual complete
local observation files. Their timer begins before CLI import and includes worker
startup, output callbacks, publication checks, file delivery and close; it excludes
Node launcher startup and build-hash bookkeeping. The repository-organization CLI
samples use `organization repository --json`; modules samples use `modules --json`.

All 16 full CLI samples exit 0 without observation warnings. None meets the
script's wall/monotonic-clock suspension flag. All eight journeys complete and
retain exact repeated module/dependency results. Raw reports preserve GC-assisted
memory samples, but RSS/high-water behavior is not used to claim precise release.

Repeated direct modules average about 15% faster at both sizes, and first
organization/project requests improve in these samples. Opening is essentially
unchanged. Full CLI differences range from a small slowdown on the smaller modules
case to modest improvements on the larger cases; there is no evidence here of a
large end-to-end speedup. Validation still takes substantial time and grows with
artifact count. Two local repetitions do not establish statistical significance
or a general performance guarantee. No validation pass, input coverage, ownership
check or evidence content was removed to improve the timing.
