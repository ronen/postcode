## Scope and result

Packages 1–3 are implemented for the M2 review gate. C13 was also completed while
changing organization claim construction. Packages 4–8 and integrated M5 acceptance
remain outstanding. This record does not certify foundation readiness or the
investigator integration.

The harness compares complete structured views, rendered output and observations
without replacing arbitrary session-shaped text. It preserves record digests,
foreign references, supporting relationships, qualification, omissions and order.
Bare reference collections require an explicit producing session. JSON rendering
must retain its exact pretty-print layout; only Unicode headings naming the producing
session are renamed, including embedded module detail. Mixed group/module inspection
is covered in both formats. The historical snapshot-to-session conversion script retains its distinct
migration-specific policy and is not used to certify this slice.

Sink assertions now execute in test bodies; interaction callbacks retain errors,
finish cleanup and rethrow. Shared CLI collection requires explicit opt-in for
expected delivery warnings. Temporary-directory cleanup is registered before
fixture setup. Comparison workers are owned before opening and both closes are
attempted independently. Subprocess tests resolve the build containing the test,
rather than assuming a different checkout build.

Evaluators return store-owned frozen outcomes. The provider freezes its retained
results before exposing them. Root module and expansion outcomes publish in one
batch. Pure organization and dependency-organization results reuse deterministic
stored outcomes, including unavailable/partial results; provider acquisition,
revision-sensitive retry and historical support remain separate. The provider
reads a context's first input support from the store instead of a duplicate map.

The evaluation index publishes only after validation and queries only the selected
session's evaluations. Existing identical records retain their owned object after
full resubmission validation. Reference allocation validates complete requests,
stages additions by session/kind, sorts new bindings within each batch and preserves
existing bindings. It makes no order-independence claim across separate calls.

## Intentional differences and version assessment

- `postcode/program-records@18` becomes `@19`: identity-key construction now
  normalizes explicit local reference positions rather than replacing text in the
  serialized key. Literal names, paths, evidence, reasons and selectors remain
  literal. Foreign references retain their namespace. The central record-identity
  method is the responsible version; language-analysis methods and canonical
  serialization remain unchanged. The method list is captured in input support,
  so this also changes input-record identities even in ordinary fixtures.
- `postcode/presentation@23` becomes `@24`: qualification policy is shared, and
  composition qualification is classified by an exact registered method token,
  rather than a prefix that also matches unrelated methods. The existing
  semicolon-separated method identities suffice; no domain qualification codes or
  new view fields were needed. Actual composition-method upgrades change the
  shared identity constant used by both producer and classifier. Limitation prose
  represented by the module run summary is defined once and remains unchanged.
- The authorized follow-up corrects idle Ctrl-C under `TERM=dumb`. Node ignores the
  editing keys used by the previous implementation in this mode. The shell now
  resets both retained line and cursor after the usual visual deletion. Tests cover
  dumb and normal terminal modes. The API's joint line/cursor requirement is
  documented in [Node readline](https://nodejs.org/api/readline.html#rlline).
- Invalid expansion publication leaves no root-only outcome. Producer/consumer
  mutation cannot change retained outcomes. Valid analysis content is preserved.
- Same-batch compact-ID collision allocation now follows sorted IDs rather than
  caller order, as required by the plan; previously bound spellings are preserved.

The identity tests include a controlled real-provider UUID with ambient modules
named by its own session and by the literal word `session`. They remain separate
and selectable. A separate controlled execution of the original baseline reproduces
`Immutable record collision` for those same two names, while the final M2 build
returns two modules. Other negative controls cover literal selectors, nested names,
paths, qualification text, foreign references and literal objects with an `id`
field. Known internal-record selectors are normalized only after establishing
that they identify a selected entity; ordinary selectors remain literal.

## State/consumer matrix

`completedMaterialization` means only completed execution and full materialization.
The following conditions preserve the pre-change consumers; they do not introduce
new store validity restrictions or a universal reuse/establishment rule.

| Consumer | Preserved decision |
| --- | --- |
| Module evaluation reuse | Root and all requested expansions completed/full, or an explicit validated provider retry basis. Neither availability nor applicability is newly required. |
| TypeScript expansion/composition/dependency caches | Completed/full entries survive acquisition revisions; incomplete entries require their captured acquisition revision. |
| TypeScript combined discovery cache | Every selected component must remain stable against acquisition; completed/full components are reusable independently of later acquisition. |
| Module projection population | Completed/full module evaluation. |
| Organization placement derivation | Completed/full module evaluation plus available repository evidence and fully materialized placements. |
| Organization projection population | Completed/full organization evaluation; non-repository subjects additionally require completed/full placement. |
| Store negative group-presence validation | Completed/full placement; no new availability/applicability requirement. |
| Dependency graph root establishment | Applicable, available and completed/full module and dependency evaluations. |
| Dependency organization establishment | Available and completed/full basis; applicability is not newly required. Endpoint materialization/classification checks remain separate. |
| Module rendering: complete analysis, export absence and final export status | Applicable, available and completed/full relevant outcomes. |
| Module rendering: composition limitation suppression | Completed/full composition outcome, independently of availability/applicability, as before. |
| Composition annotation | Applicable, available and completed/full outcome when no positive composition claim exists. |
| Dependency presentation completeness | Applicable, available and completed/full outcomes. |
| Organization presentation: direct-module absence | Placement materialization alone, unchanged. |
| Pure organization derivation reuse | Exact deterministic ID over immutable stored bases; independent of outcome state. Replaces session maps that cached only completed/full derivations. |

The synthetic state test stores and reuses all availability/applicability
combinations with completed/full outcomes. Existing incomplete-provider retry,
new-acquisition revision and historical-support tests remain passing.

## Verification evidence

- `npm run check`: passed.
- `npm test` on the final application source/build: 248 tests passed, none failed,
  skipped or cancelled. This includes existing semantic fixtures and new ownership,
  atomicity, binding, identity, graph-oracle and comparator controls.
- Deliberately wrong interaction expectations rethrow `AssertionError` after
  cleanup. A sink assertion caught by production delivery handling causes the
  shared CLI collector to reject its unexpected warning, also as an assertion.
  Explicitly expected sink failures preserve successful command status.
- Independent graph oracle pins component and member order, child/root indices,
  isolates, self-loops, all parallel internal claims and incomplete-root gating.
- Evaluation query operation counts visit one outcome with both 10 and 1,000
  unrelated input records. No wall-clock performance threshold is asserted.
- Pure unavailable organization and dependency-organization repetition submits
  zero additional batches; a changed immutable module basis derives a new result.
- Invalid coupled expansion publication leaves no evaluation-index residue and the
  next valid root remains attempt 1. Invalid entity requests leave no binding
  residue, and stale staged allocation cannot steal an existing binding.
- The native compiler probe's first compiler-phase marker is retained. Its
  80,000-declaration control publishes and finishes; one SIGINT in compiler work
  exits by SIGINT with no view or finish marker. See [probe data](m1-compiler-probe.json).

(the parent of task opening) matches audited application baseline

[Ownership comparison](m2-ownership-comparison.json) covers 72 complete CLI runs
between the original baseline and the ownership checkpoint before identity/version
changes. All compared structured views, exact output, command outcomes and
observation relationships agree after reference normalization.

[Final comparison](m2-final-comparison.json) covers 72 runs against the final M2
application build. Its control is the original baseline build with exactly two
constant substitutions: `program-records@18` to `@19`, and `presentation@23` to
`@24`. The old identity algorithm and all other baseline behavior remain intact.
This deliberately aligns version attribution for ordinary-input comparison; it
is not a claim of byte equality between the two unmodified releases. The literal
identity fixes and authorized behavior changes are verified separately above.
The comparator does not erase version fields, record digests, changed order or
qualification. The script checks build fingerprints at start and completion.

Both comparison sets cover module inventory, project/repository organization,
inspection, dependencies, children and parents, JSON/Unicode, and explicit source
detail. Fixtures are dependency-journey, dependency-contract, exports, and a
deterministically generated 80-module chain with 240 non-module artifacts across
24 artifact directories. This exercises substantial exported surfaces and bounded
display; it is not an integrated performance measurement.

[Session comparison](m2-session-comparison.json) covers 216 comparisons of complete
views and output across fresh direct sessions, accumulating worker sessions,
reversed request order and retained repeated requests on the final M2 source.
Each fixture has 18 requests and three comparison paths.

The JSON reports retain build SHA-256 fingerprints and per-command result hashes.
Absolute temporary configuration paths have been replaced by fixture labels and

## Native scope and limits

Verified on macOS 26.6.2 (25G83), Node 22.13.1, process architecture x64,
TypeScript 6.0.3. Checkout, operating-system fixture directory and observation
destination were local APFS (native `statfs` type 26). No Linux, Windows or network
filesystem verification is claimed.

The remaining acquisition and publication failure probes belong to M3; no async
Git ownership, deadline, cancellation escalation or atomic observation-publication
guarantee is claimed at this checkpoint. Graph-library integration, selected-view
indexing, display-cell/grapheme handling, option-parser migration and integrated
performance measurements remain for M4/M5. Review should examine the policy and
callers directly rather than treating these passing checks as proof of correctness.
