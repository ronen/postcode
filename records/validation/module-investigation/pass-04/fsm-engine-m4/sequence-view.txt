@investigram-2d65ea4b · interpretation
`FsmEngine` separates a one-time definition phase from per-instance execution. `define()` lets `FsmBuilderImpl` record the DSL, validates it immediately, compiles lookup tables, and closes over that definition in a typed factory. Every factory call then creates an independent machine with its own current state, context reference, event queue, timer registry, trace settings, and instance identifier; construction immediately runs the initial state's entry actions. The context is not copied: `fsm.context` and action callbacks receive the same mutable object supplied to the factory.

A top-level `dispatch()` is synchronous for the complete resulting work batch. It appends the event, then drains the FIFO until empty. A dispatch made from a guard or action only appends another event and returns; that event is processed after the current event—including its transition and entry work—finishes. If processing throws, the outstanding queue is discarded and the outermost dispatch rethrows, but prior context mutations and already-completed actions are not rolled back.

For each event, the engine first distinguishes an event absent from the entire compiled definition (`FsmEngineUnknownEventError`) from one known somewhere but unavailable in the current state and fallback (`FsmEngineUnhandledEventError`). For a known event, it runs the current state's begin actions, examines transitions in declaration order, and selects the first transition whose guards all pass. If no state-specific transition wins, it runs any fallback begin actions and tries fallback transitions. If at least one state or fallback transition exists but all guards reject it, the event is considered handled by an implicit no-action stay; if no transition exists in either place, it is unhandled. Thus begin actions can mutate context before guards, and state-specific begin actions can run even when fallback handling is ultimately selected.

An internal `stay()` executes only its transition actions. An external `toState()`—even when its target equals the current state—executes old-state exit actions, transition actions, commits the target, and then executes target-state entry actions. Consequently, an exception before the commit leaves the old state selected; an exception from an entry action occurs after the new state has been selected. Re-entrantly queued events do not interrupt these steps.

Actions receive the mutable context and a restricted action API; guards receive readonly-typed payload/context views, although that is a TypeScript constraint rather than runtime immutability. Metadata distinguishes begin, transition, exit, ordinary entry, and initial entry calls. Tracing can use a custom logger and records event handling, guard outcomes, selected transitions, and action invocations with a machine/instance label.

Timers are per instance and keyed. A missing key defaults to the event name; scheduling the same key replaces the old timeout. Relative delays and `performance.now()`-domain deadlines are supported, negative or past values become zero-delay timeouts, and `Infinity` means no timeout is installed. Expiry dispatches through the same queue, so it does not bypass normal event semantics. The public action type and README say a payload-bearing timer dispatches its supplied payload, but the captured adapter constructs an empty argument list when the `payload` property exists and an `[undefined]` list when it does not. Read literally, payload-bearing timer events therefore lose their payload; this is a documentation/type-contract versus implementation discrepancy, not an executed observation.

@investigram-7edddb44 · interpretation
The engine's action API is intentionally narrower than the full instance: callbacks can enqueue typed events, schedule an event, or cancel one/all timers. `TimerRegistry` owns the timeout handles and removes a handle before invoking its callback, which permits that callback to schedule another timeout under the same key. When a timeout fires, its callback calls the engine's ordinary `dispatch()`. The intended typed contract requires `payload` for payload-bearing events and forbids it for void events, but the captured engine adapter reverses the argument-list construction test, so supplied timer payloads appear to be dropped.

@investigram-26489d1b · interpretation
The practical event algorithm is: enqueue; if another dispatch is active, return; otherwise repeatedly dequeue, reject globally unknown names, run current-state begin actions, try current-state transitions, then run fallback begin actions and try fallback transitions. Events queued during any of those callbacks wait until this whole event finishes. An event with declared transitions that all fail guards is an implicit successful stay, whereas a known event with no transitions in the current state or fallback produces an unhandled-event error after any applicable begin actions have run.
