### Actionable findings

**F1 (medium): current user-facing guides still describe the retired correction/replacement regime.** The plan's M4 says to "retire superseded legacy mechanisms and misleading documentation", and handoff focus 6 asks whether current documentation accurately describes delivered behavior. The architecture, capability and CLI references were updated, but two current guides were not:

- `README.md`, "Progressive investigation" (about lines 187–194), is unchanged across the whole implementation range. It says repeated requests make a fresh selection "including accepted corrections and current associations". It says `inspect @investigram-…` "selects the original historical account with its current revision context". It says `--revision-page <n>` gives "further correction/cause rows". Under the delivered model there are no corrections. Fresh selection preserves all standing alternatives, and revision pages cover captured change grounds, qualification groups and inconsistency reports (as `docs/cli-reference.md` now says).
- `docs/hosted-investigation.md` (about lines 241–251) says "Fresh selection chooses current replacement accounts". It says "Views expose correction links, unresolved alternatives and citation-based reconsideration warnings". It also says "the investigator receives bounded correction and cause context with further revision pages available". All three describe the removed primary-replacement, correction-context and citation-closure behavior. The pass-05/pass-06 paragraphs that follow are historical evidence and can stay, provided they are framed as historical (as `STATUS.md` now does).

Suggested resolution: rewrite those passages to match `docs/cli-reference.md#progressive-investigation-and-usage`, and mark historical assessments as concerning the earlier representation.

**F2 (low): the CLI reference keeps a transitional notice that tells the reader to remove it at completion.** In `docs/cli-reference.md`, "Common contribution integration" (around line 95), the second paragraph still reads "The task updates affected command behavior … as implementation proceeds … At completion, remove this notice and document the actual supported routes and limitations." The capability reference dropped its equivalent sentence, but this one remains, so the closure claim and the notice contradict each other. The phrase "Subject navigation such as `inspect @investigram-…` makes a fresh selection with current revision context" (around line 129) also uses the retired framing. Suggested resolution: replace the notice with a short statement of the delivered CLI scope (no state/option commands; API-only routes), and reword line 129.

**F3 (low): the retirement left `retainedPresentation` orphaned, and a test now verifies the orphan instead of the production path.** After `retained-presentation.ts` was deleted, `retainedPresentation` in `src/lib/presentation-contracts.ts` has no production caller. Exact presentation compatibility lives in `application/executor.ts` (`retainedFacts`, `unsupportedOptions`, `consumptionPlan`, `settleConsumption`). The final delta still edited the helper's semantics: `revision` now covers `contribution`/`contribution-inspection`, where the production path adds `revision` for `contribution-inspection` itself. So the two implementations can now drift. `test/exports-lens.test.ts` (around line 207) replaced its production `presentRetained` refusal check, which asserted `reason: 'presentation-unavailable'` and `retainedAnswers`, with a direct call to this helper. Equivalent production coverage does exist in `application-exact-compatibility` ("direct exact exports refuses missing declared support…" and the partial/empty CLI exact cases), so no behavior is untested. However, the inventory describes the `exports-lens` change as resolving "through `application/retained.ts`", and the refusal half no longer does. `planPresentation`/`compatiblePresentation` have no callers either (already true before M4). Suggested resolution: remove the orphaned helper(s), or drop or redirect the assertion to the executor, and adjust the inventory line.

**F4 (low): one ported evidence test lost its attribution assertion to a near-vacuous check.** In `test/evidence-access.test.ts`, "realistic dialogue follows delegation and group documentation through bounded tools", the old assertion checked that the delivered dependency-evaluation summary was attributable without claiming full-record delivery. The replacement is `assert.ok(result.production.deliveries.length > 0)`. The common dialog records a baseline identification acquisition before any tool exchange (as the inventory itself notes for `work-attribution`), so this holds regardless of the delegation exchange. The neighboring documentation test does assert `production.evidence` equals the full records seen, so the semantics are covered once. Suggested resolution: give the delegation test the same `production.evidence` set assertion, and optionally assert that summary-only evaluation records are absent from it. This matters for focus 1's "meaningful coverage rather than merely making the suite pass".

**F5 (low, pre-existing gap relied on by the closure claim): the runtime guard against legacy `interpretation` registration has no test.** `application/catalog.ts` rejects `requirements.kind === 'interpretation'`. This delta moved that check ahead of `mechanicalImplementation`, and the architecture README cites it ("application registration rejects earlier interpretation requirements") as part of the no-legacy-bypass claim. No test asserts it, either at `1e99e93` or at the target. I confirmed by hand that it works. Suggested resolution: add one small catalog test (built-in id and new id) so the closure claim is regression-protected.
