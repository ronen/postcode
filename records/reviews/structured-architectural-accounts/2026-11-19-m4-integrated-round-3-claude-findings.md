### Independent derivations (no defect found)

These are the focus areas that rounds 1 and 2 reported as spot-checked only. I traced each one through source.

- **Atomic acceptance (focus 1, 4).** `ContributionLedger.accept` stages the whole pool before any state change. Staging covers identity resolution (native identity before allocation, with kind/modality conflict rejection), reference and role checks, content-contract acceptance, the cross-pool component, designation and finite-membership checks, report-answer targeting, owned captures and identifying-name extraction. Only then does it commit. I found no realistic throwing path after the first mutation. Mechanical qualifications must name a Claim context of their own method. Agentic qualifications cannot raise their status, assert a guarantee or adopt a provider context. Evidence must have been supplied to that same production, so one batch does not union producers' exposure. Cross-production local references within one batch are deliberate (native findings plus their policy uses) and remain separately attributed.
- **Cause derivation (focus 3).** `ContributionStatus.#derive` treats as known only changes that were actually delivered: by notice, by declaration delivery, as disclosed displacements, or as identified concerns. A listing that merely reflects a change does not make it known. A production's own declarations never become its causes. Exact, membership, inherited and scope routes compare against the delivery position. Removal causes apply only to current-only inventories, while additions apply to both inventory kinds. Inherited causes can only form an acyclic chain, because a production can receive only content that had already been accepted.
- **Dispatch versus acquisition (focus 3).** `conductDialog` checkpoints at each actual dispatch. It discards acquisitions that were never dispatched (a limit, interruption or invalid exit), and also discards responses withheld by the response bound, including the export enrichment. Notices are recorded only for the exchange that carries them. Changes accepted after the last dispatch therefore remain causes. Answer assembly (`selectContributionAnswer`, `answerSupport`, inspection) uses the ledger directly and never opens a production. Native wrappers record their caller-supplied inputs as item deliveries.
- **Reuse, fresh work and outcomes (focus 2).** Ordinary reuse keys on the canonical whole request plus the definition/catalog method digest. It prefers an accepted attempt, reuses completed non-transient failures, and retries communication/configuration failures. This matches the pre-migration `bd92670` contract and the capability reference. A fresh request shares the repeated question's Query result and is never reused. Attempt fulfillment counts only the attempt's own or explicitly returned designations. Answer fulfillment is assessed separately against current designations, so a reused attempt's historical fulfillment cannot mask `no-current-answer`. Answer identity excludes attempt reporting.
- **Ownership (focus 4).** `ImmutableCapture` shares only graphs it has itself copied and frozen. Externally frozen nodes are copied, accessors, proxies and exotic prototypes fall back to native cloning without trust, and disposal turns later captures into untracked clones. Session close releases ownership through `releaseOwnership`.

### Actionable findings

**F1 (low): the arrangement claims an unfulfilled request even when no diagram was requested.** `arrangeContributionAnswer` (`src/lib/contributions/answers.ts:259`) emits "A diagram can be drawn for N of M alternatives; the request is not fulfilled for the others" whenever more than one alternative exists and only some of them select a drawable state model. It does not consult the answer's `fulfillment`, which is `null` when no result contract applies. The CLI renders these notices for every contribution answer (`interfaces/cli/contribution-presentation.ts`). The state-model guidance is also given to `examine-content` and is reachable by follow-up options without the diagram contract, so state models can appear in non-diagram answers. A throwaway probe confirmed the behavior. It used two standing designations of a result with `resultContract: null`, one selecting a state model and one prose-only. The answer had `fulfillment: null`, yet the view carried the "request is not fulfilled" notice. This misstates request fulfillment, which the plan and the attempts/answers decision keep distinct from selected meaning. No test covers the notice in either the diagram case or the non-diagram case. Suggested resolution: emit the fulfillment clause only when the projection's fulfillment is non-null (or base it on the retained per-alternative `unmet`), keep a neutral "diagram available for N of M" statement otherwise, and add a test for both cases.

**F2 (low): current descriptive documentation still names the removed binding port and revision snapshots.** Round 1 F1 corrected the README and hosted guide, but two current passages remain unchanged across the whole branch:
- `docs/architecture/README.md:392–395`: "Investigation selections are retained Projections with unpaged revision snapshots; … with coordinated reference bindings or a restricted binding-only port." M4 deleted the binding port (`m4-retirement-coverage.md`, "the obsolete revocable binding port … deleted"), and the revision-snapshot selections were retired with it.
- `docs/capability-reference.md:13`: "Exact retained-answer presentation also preserves the selected accounts and revision snapshots." Its claim that retained interpretations "originate in module investigation" also no longer covers selected-content and follow-up investigations.

Suggested resolution: rephrase both passages in the current terms already used elsewhere in the same documents: designated answers with independently captured standing, change context and coordinated bindings. This is the same class as round 1 F1, under the plan's M4 instruction to retire misleading documentation.

**F3 (low, latent): explicit option-request `context` is retained and identity-bearing but never delivered.** `InvocationRequest.context` is documented as "explicitly selected input context". The ledger validates and retains option `request.context` (`ledger.ts:512`), and the follow-up route forwards `option.request` unchanged into `invoke`, where `context` participates in the request key. However, `conductDialog` builds initial input only from `request.subjects`, the option metadata and, for fresh requests, the current designations. It never acquires the context entries, and `DialogInput.request` omits them. The invoked agent sees them only as addresses inside the option metadata, with no delivery. The hosted schema does not let agents author option `context`, and ordinary requests always pass `[]`, so no supported path reaches this today. A controlled or future producer could still author an option whose stated context is silently not supplied. Suggested resolution: either deliver the context entries as initial input under the same capture and exposure contract as subjects (as the selected-content-input row of the plan implies), or reject non-empty option context at acceptance until it is supported. A short test would settle it either way.

### Non-defect observations

- At most 24 change notices are delivered per exchange (`noticesPerExchange`), and the agent is not told that more are pending. Undelivered ones correctly remain causes, so exposure accounting is truthful. The agent simply cannot ask for the rest. This may be worth recording as a guidance limit.
- `ContributionLedger.#subject` throws a plain `Error` (rather than `UnknownReference`) for an unknown component or a non-result designation. The supported callers pre-validate subjects (`contributions/subjects.ts:47`), so this is not reachable from requests.
- The pool-wide namespace for investigram and Entity local keys means two independent productions in one acceptance cannot reuse a local key. Only native wrappers batch productions, and they use provider-derived keys.
