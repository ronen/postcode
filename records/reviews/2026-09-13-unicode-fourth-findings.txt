## Overall assessment

The module inventory is now successful as a compact starting view. It is easy to
scan, exposes both convenient handles and precise Entity IDs, gives useful export
recognition cues without overloading the list with type information, and keeps
display omissions distinct from analysis status and run limitations.

Normal inspection is also close. Selection cardinality, export roles,
documentation status, and Entity ID are all legible. The exception suite is a
valuable addition and shows that empty, partial, unavailable, failed, stopped,
aliased, and multiply-declared cases are not silently flattened into ordinary
success.

I would accept the normal inventory presentation now. I would make the source
detail usable and clean up the smaller items below before considering the whole
presentation set finished.

## 1. Rework source detail as a human-facing expansion

This is the one substantive remaining issue.

The source-detail section is explicit, bounded to displayed claims, visibly
separate, and correctly labelled as a source escape. Those architectural
properties are good. Its content, however, is currently dominated by full
internal claim record keys followed by byte offsets and lengths:

    Claim snapshot:...:documentation-association:...
      /path/origin.ts · offset 58, length 26

That is auditable machine provenance, but it is not an effective human source
view. A person cannot readily tell which conceptual item a record supports, and
offset/length pairs require another tool or calculation before the relevant
source can be read.

Organize source evidence by the conceptual items already displayed, using their
human labels. Prefer line and column ranges and include a bounded source snippet
where useful. For example:

    SOURCE DETAIL — explicit source escape
    Source locations and excerpts supporting displayed claims only.

    Module origin
      fixtures/exports/origin.ts

    Export Merged
      fixtures/exports/origin.ts:3:1
        export interface Merged { ... }
      fixtures/exports/origin.ts:8:1
        export interface Merged { ... }

    Documentation for Merged
      fixtures/exports/origin.ts:2:1
        /** First contribution. */

Exact formatting and snippet granularity remain presentation choices. The
important requirements are that a reader can associate each source item with the
displayed claim and can understand the selected evidence without decoding an
internal record key. Full claim IDs may remain in JSON or behind a more diagnostic
option; they should not be the primary Unicode organization.

Also reconsider the module-level provenance span of `offset 0, length 571`, which
appears to cover the whole source file. It does not disclose the contents, but it
is not a very selective location. A file-level source association should be
labelled as such rather than represented as though the entire file were one
precise claim span.

## 2. Remove the ordinary `implementation-available` facet

The earlier review identified `implementation available` as superfluous in these
normal project-module views, but it remains in both headings:

    Project modules · 18 · TypeScript names not established · implementation-available
    Selected modules · 1 · TypeScript names not established · project, implementation-available

The facet is legitimate domain data and can matter when contrasted with ambient,
declaration-only, virtual, or opaque modules. Repeating it for every ordinary
implemented module adds noise without helping this view. Suppress it in the
ordinary homogeneous case and retain it when it distinguishes modules or explains
an exceptional one.

The `project` facet in a one-module inspection is similarly low-value, although
less distracting. It can be suppressed when the section already says that the
selection contains project modules.

## 3. Wrap documentation text to a usable width

The repeated sentence `A bounded documentation assertion.` is synthetic fixture
content used to force truncation; it is not text generated by PostCode, and the
phrase has no domain meaning. The test is valid, but its wording resembles a
PostCode qualification closely enough to mislead a reviewer about where the text
came from. Replace it with unmistakably synthetic content, such as numbered test
segments, or label the validation case's input more explicitly.

The actual presentation defect exposed by the fixture is that the retained text
is emitted as one extremely long physical line. The example bounds the assertion
correctly, but character bounding alone does not make Unicode output readable.
Wrap documentation at a reasonable display width while preserving its indentation
and then report the omitted character count.

The local line:

    … 449 assertion character(s) omitted.

already explains the truncation precisely. The later display item:

    documentation for 1 listed module

is less accurate: documentation was displayed, and only part of an assertion was
omitted. Either remove that aggregate item for inspection or describe what was
actually omitted, such as characters from one documentation assertion. Do not
imply that all documentation for the module was omitted.

## 4. Make zero-match wording direct

The zero-match heading currently says:

    0 modules selected from 4 · exact matches for absent

Use singular, direct failure wording instead:

    0 modules selected from 4 · no exact match for absent

This makes the result immediately understandable and distinguishes it naturally
from the valid multiple-match case.

Because a zero-match inspection has no selected module, its generated generic
“Next · inspect a module” command is defensible, but a short cue that the subject
may be replaced with a handle or Entity ID from `modules` would be more useful
than silently repeating the normal footer.

## 5. Tailor the inspection footer

After a successful inspection, the output again says:

    Next · inspect a module:

and supplies the same generic command. This is no longer the user's obvious next
step. At minimum say `inspect another module`. Better, the successful inspection
footer could make the two meaningful continuations apparent without becoming a
miniature manual:

    Next: replace MODULE_HANDLE to inspect another module; add --source-detail
    to show supporting source evidence.

The generated command itself is now much better: unnecessary shell quoting and
the long replacement instruction are gone, and `MODULE_HANDLE` is a safe visible
placeholder.

## 6. Keep the qualification structure

The current distinction is sound:

- `Display` reports what this rendering omitted;
- `Status` states what the analysis established and its coverage boundary; and
- `Run limitations` reports qualifications of this run/input capture.

The coverage statement is general to this analysis method, while the generated
location count and non-atomic input capture qualify the particular result. The
general coverage sentence is still important enough to keep in ordinary output:
without it, “174 modules found” could be mistaken for an unqualified complete
population. User documentation may explain it more fully, but should not become
the only place where this result-defining boundary is visible.

The compact successful capability line is also effective. Expanded capability
states appear only for the exceptional partial/unavailable/failed/stopped cases,
where the extra detail is needed.

## 7. Small documentation refinements

The command reference is now a useful first-use guide and accurately explains
names, handles, Entity IDs, snapshots, selection multiplicity, `(none)`,
qualifications, observations, and the conceptual/source boundary.

Update its source-detail description along with the presentation. It currently
says only that source locations are displayed. If the Unicode expansion gains
bounded excerpts, say locations and excerpts, without promising full-file
rendering.

The sentence “JSON lists the full selected inventory” in the Unicode display is
potentially ambiguous beside the reference's statement that JSON includes only
bounded export and documentation cues. It appears to mean the full module
population rather than every related record. Prefer:

    JSON lists all selected modules with bounded related detail.

or another wording that names exactly what is complete.

## What is now working well

- The inventory is compact and visually aligned without sacrificing long values.
- Handles omit the redundant `module-` prefix.
- Entity IDs are short, type-prefixed, and shown beside handles.
- Duplicate handles are honestly supported and demonstrably select multiple
  modules.
- `(none)` unambiguously represents an established empty export set.
- Export names are useful recognition cues without redundant type/value markers
  or export counts in the inventory.
- Inspection restores type/value roles and meaningful exceptional provenance.
- Re-export aliases, semantic symbols, origins, wildcard forwarding, and multiple
  contributing declarations remain visible when relevant.
- Recorded documentation assertions are clearly distinguished from established
  truth.
- Partial and unavailable results say “not established” rather than pretending
  that no exports exist.
- The command placeholder and Entity ID/snapshot separation are now practical.
- General coverage, per-run limitations, and display omissions are no longer
  blended into one undifferentiated qualifications block.

## Recommended completion threshold

Before presentation acceptance:

1. make source detail human-readable and associated with displayed conceptual
   items;
2. remove ordinary `implementation-available` noise;
3. wrap long documentation and correct its omission description; and
4. fix zero-match wording.

Tailoring the successful-inspection footer and tightening the JSON-description
wording are worthwhile usability polish, but neither should block the slice if
the higher-priority items are resolved.
